## 2. Статус по режимам работы

| Режим | Захват | Фильтрация по процессу | Состояние |
|-------|--------|------------------------|-----------|
| **WinDivert** (`capture_mode=windivert`) | Драйвер WinDivert, модификация DST в SYN | ✅ Да — `WinDivertCapture::CheckProcessRule`, решение на **каждый** пакет (устойчиво к запаздыванию TCP-таблицы) | Собирается, статически корректен |
| **Wintun embedded** (`wintun.engine=embedded`) | lwIP 2.2.0 внутри процесса | ✅ Да (новое, Задача 2) — `Tun2SocksEngineEmbedded::DecideFlow`, решение **один раз на SYN** | Собирается; есть замечания по локингу (см. п. 3.1) |
| **Wintun external** (`wintun.engine=external`) | Дочерний `tun2socks.exe` + SOCKS5 | ❌ **Нет** (архитектурное ограничение) | Собирается; супервизор процесса надёжен |

### Что проверено статически по каждому режиму

- **WinDivert:** порядок остановки корректен (M11 — capture → pipe → relay →
  table), `windivert_debug.log` теперь пишется в общий каталог
  [`GetLogDirectoryW()`](../src/service/TcpRedirectorService/infrastructure/paths/AppPaths.h:94)
  (`<exeDir>\.logs\`) и подпадает под общую retention-очистку.
- **Wintun embedded:** RAII-уборка в `WintunCapture::TearDown` (LIFO: движок →
  сессия → маршруты → адаптер), корректный `RouteScope` при провале Open().
  Фильтрация по процессу реализована через переиспользуемый
  [`ProcessResolver`](../src/service/TcpRedirectorService/infrastructure/process/ProcessResolver.h)
  (TTL-кэш PID под `SRWLOCK`).
- **Wintun external:** дочерний процесс изолирован в Job Object с
  `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` (нет процессов-сирот), graceful-стоп
  через `CTRL_BREAK_EVENT` + force-kill, авто-рестарт с backoff и лимитом
  перезапусков в минуту.

### Явное ограничение external-режима (задокументировано в коде)

В [`WintunCapture.cpp:295-313`](../src/service/TcpRedirectorService/infrastructure/capture/WintunCapture.cpp:295)
external-движок **не поддерживает фильтрацию по конкретному процессу**: на
границе SOCKS5 источником любого соединения является сам `tun2socks.exe` (его
PID), а не исходное приложение, и `tun2socks` не сохраняет source-порт
оригинального приложения. Поэтому при `process_filter_enabled=true` для external
в лог выдаётся предупреждение, и **весь** трафик туннеля проксируется. Для
пер-процессной фильтрации нужно использовать `engine=embedded` или
`capture_mode=windivert`.

## 3. Известные проблемы и баги

### 3.1. [Средняя] `DecideFlow()` в embedded-движке выполняется под `m_core_lock` (расхождение с документацией + латентность)

- **Файлы/строки:**
  [`Tun2SocksEngineEmbedded.cpp:557-568`](../src/service/TcpRedirectorService/infrastructure/capture/wintun/Tun2SocksEngineEmbedded.cpp:557)
  (`EngineThreadMain` держит `std::lock_guard<std::recursive_mutex> lk(m_core_lock)`
  вокруг `nf->input(p, nf)`), которое вызывает
  [`EngineTramp::OnAccept`](../src/service/TcpRedirectorService/infrastructure/capture/wintun/Tun2SocksEngineEmbedded.cpp:218)
  → [`DecideFlow`](../src/service/TcpRedirectorService/infrastructure/capture/wintun/Tun2SocksEngineEmbedded.cpp:454).
- **Описание:** комментарий в заголовке
  [`Tun2SocksEngineEmbedded.h:194`](../src/service/TcpRedirectorService/infrastructure/capture/wintun/Tun2SocksEngineEmbedded.h:194)
  утверждает: «Вызывается ВНЕ core-lock (резолв PID может быть тяжёлым)». В
  действительности `OnAccept` (а значит и `DecideFlow`) вызывается из
  `tcp_input`, который движок вызывает **удерживая** `m_core_lock`. Внутри
  `DecideFlow` выполняются потенциально долгие операции:
  - скан TCP-таблицы `GetExtendedTcpTable` (при промахе кэша),
  - `Sleep(20)` — единичный ретрай при ненайденном PID
    ([`Tun2SocksEngineEmbedded.cpp:467`](../src/service/TcpRedirectorService/infrastructure/capture/wintun/Tun2SocksEngineEmbedded.cpp:467)),
  - обход дерева процессов `IsDescendantOf` (снимок `CreateToolhelp32Snapshot`),
  - **блокирующий `::connect()`** к relay/оригинальному DST
    ([`Tun2SocksEngineEmbedded.cpp:259`](../src/service/TcpRedirectorService/infrastructure/capture/wintun/Tun2SocksEngineEmbedded.cpp:259)).
- **Влияние:** на время принятия каждого нового соединения весь lwIP-стек
  (все прочие активные flow'ы) простаивает под общим `m_core_lock`. При
  «холодном» кэше PID и/или медленном `connect` это заметная пауза (десятки мс).
  Корректности не нарушает, но снижает пропускную способность/латентность при
  всплеске новых соединений.
- **Предлагаемое исправление (не выполнено — риск для логики):** выносить
  резолв PID и установку исходящего сокета за пределы `m_core_lock` (например,
  принять pcb в accept, а `DecideFlow` + `connect` выполнять асинхронно в
  отдельном потоке, регистрируя flow после готовности), либо как минимум убрать
  `Sleep(20)` из-под лока. Требует аккуратной работы с lwIP callback-контрактом,
  поэтому оставлено как рекомендация.

### 3.2. [Средняя] Embedded-движок: решение PROXY/DIRECT/BLOCK принимается один раз на SYN

- **Файл:** [`Tun2SocksEngineEmbedded.cpp:470-475`](../src/service/TcpRedirectorService/infrastructure/capture/wintun/Tun2SocksEngineEmbedded.cpp:470).
- **Описание:** в отличие от WinDivert (где `CheckProcessRule` пересматривается
  на каждый пакет), embedded решает судьбу flow однократно на accept. Если к
  моменту SYN TCP-таблица ОС ещё не содержит запись о сокете-источнике, PID не
  резолвится даже после единичного `Sleep(20)`, и flow уходит в **DIRECT** (в
  обход прокси) без возможности пересмотра.
- **Влияние:** для «быстрых» приложений, чей SYN опережает появление записи в
  таблице, возможен ложный DIRECT — приложение, которое должно было идти через
  прокси, единично пойдёт напрямую. Вероятность низкая (есть ретрай), но
  ненулевая.
- **Предлагаемое исправление:** увеличить число/интервал ретраев или отложить
  окончательное решение до первого data-сегмента. Оставлено как рекомендация.

### 3.3. [Средняя] `ConnectionTable`: составной ключ применён только на записи, но не на чтении (M3 — неполное исправление)

- **Файл:** [`ConnectionTable.h`](../src/service/TcpRedirectorService/infrastructure/relay/ConnectionTable.h).
- **Описание:** `Add()` ([:69](../src/service/TcpRedirectorService/infrastructure/relay/ConnectionTable.h:69))
  корректно использует составной ключ `(src_port + orig_dest_ip)` для
  предотвращения перезаписи (комментарий «M3»). Однако `Get()`
  ([:107](../src/service/TcpRedirectorService/infrastructure/relay/ConnectionTable.h:107)),
  `GetProxyConfigId()` ([:128](../src/service/TcpRedirectorService/infrastructure/relay/ConnectionTable.h:128))
  и `IsTracked()` ([:147](../src/service/TcpRedirectorService/infrastructure/relay/ConnectionTable.h:147))
  ищут **только по `src_port`** и возвращают первую запись в цепочке коллизий.
- **Влияние:** если два одновременно отслеживаемых соединения используют один и
  тот же эфемерный `src_port` к разным адресам назначения (возможно при
  переиспользовании порта), чтение может вернуть **чужой** original-DST → трафик
  восстановится на неправильный адрес. Вероятность на практике низкая, но это
  логическая недоработка исходного пункта M3 из плана аудита.
- **Предлагаемое исправление:** передавать `orig_dest_ip` (или полный 4-кортеж)
  в `Get`/`IsTracked`/`GetProxyConfigId` и сопоставлять составной ключ на чтении.
  Требует изменения сигнатур и вызывающего кода WinDivert — не тривиально,
  оставлено как рекомендация.

### 3.4. [Высокая — безопасность] Живой IPC-канал (`TcpIpcServer`) не аутентифицирован; защищённый `PipeServer` не используется

- **Файлы:**
  [`TcpIpcServer.h`](../src/service/TcpRedirectorService/infrastructure/ipc/TcpIpcServer.h)
  (используется в
  [`ServiceMain.h:318`](../src/service/TcpRedirectorService/adapters/driving/ServiceMain.h:318)),
  [`PipeServer.h`](../src/service/TcpRedirectorService/infrastructure/ipc/PipeServer.h)
  (не подключён).
- **Описание:** служба поднимает управляющий IPC на TCP `127.0.0.1:34011` без
  какой-либо аутентификации или ACL — любой локальный процесс/пользователь может
  подключиться и отдавать команды (в т.ч. управляющие). При этом в проекте есть
  `PipeServer.h` с корректным DACL (только Administrators/SYSTEM,
  `MakeAdminOnlySA()`) и `FILE_FLAG_FIRST_PIPE_INSTANCE` — но он **не
  используется** (мёртвый код). То есть требование [C1] из
  [`plans/audit_fixes_plan.md`](../plans/audit_fixes_plan.md:11) реализовано в
  неиспользуемом компоненте, а фактический канал остался незащищённым.
- **Влияние:** локальное повышение поверхности атаки — непривилегированный
  процесс на той же машине может управлять службой через loopback-порт.
- **Предлагаемое исправление:** либо вернуться на named pipe (`PipeServer`) с
  его DACL, либо добавить к `TcpIpcServer` аутентификацию (например, проверку
  токена/секрета из защищённого файла, доступного только Admin/SYSTEM), либо
  ограничить доступ к порту фаерволом на уровне пользователя. Риск для рантайма
  высокий — оставлено как задокументированная рекомендация, логика не менялась.

### 3.8. [Низкая] lwIP embedded: не поддерживается повторная инициализация (Start после Stop)

- **Файл:** [`Tun2SocksEngineEmbedded.cpp:596-600`](../src/service/TcpRedirectorService/infrastructure/capture/wintun/Tun2SocksEngineEmbedded.cpp:596),
  [`:735-736`](../src/service/TcpRedirectorService/infrastructure/capture/wintun/Tun2SocksEngineEmbedded.cpp:735).
- **Описание:** `lwip_init()` вызывается один раз на процесс (guard
  `s_lwip_inited`), обратной `lwip_deinit` нет. После `Stop()` глобальные пулы
  lwIP остаются, флаг не сбрасывается. Повторный `Start()` в рамках одного

- **Влияние:** служба в текущей архитектуре не рассчитана на «перезапуск

  полный рестарт службы. Для типового сценария (служба запускается/останавливается
  вместе с процессом) не проявляется.
- **Предлагаемое исправление:** при появлении сценария «reload без рестарта» —
  инкапсулировать состояние lwIP в отдельный инстанс или пересоздавать процесс.

### 3.10. [Низкая] Рассинхрон версий: `VERSION`=1.0.0 vs `package.bat`/`setup.iss`=1.1.0

- **Актуальное состояние:** easy-режим частично закрыл проблему — добавлены
  guard'ы `if not defined DEPLOY/PKG_VERSION` и `#ifndef MyAppVersion`, что

  артефакт получит 1.1.0, не совпадающую с `VERSION`.
- **Предлагаемое исправление:** сделать `VERSION` единственным источником истины —
  читать его в `package.bat` и передавать в `ISCC /DMyAppVersion=...`; убрать
  жёсткие дефолты 1.1.0.

## 5. Рекомендации по улучшению (приоритизировано)

1. **Безопасность IPC (высокий приоритет).** Закрыть п. 3.4: аутентификация или
   ACL на управляющем канале. Это единственная находка с реальным риском
   безопасности.
2. **Локинг embedded-движка (средний).** Вынести `DecideFlow`/`connect` из-под
   `m_core_lock` (п. 3.1), убрать `Sleep(20)` из критической секции.
3. **Целостность `ConnectionTable` (средний).** Довести M3: составной ключ на
   чтении (п. 3.3).
4. **Синхронизация GUI ↔ служба (средний).** Добавить `process_filter_enabled` в
   GUI (п. 3.5); исправить `maxSizeMB` (п. 3.6); перевести «полные» writer'ы GUI
   на **merge с существующим JSON** вместо полной пересборки объекта, чтобы не
   терять неизвестные GUI поля.
5. **Автоматизация версии (низкий).** Единый источник версии — файл `VERSION`
   (п. 3.10).
6. **Тесты (низкий-средний).** Расширить юнит-покрытие: `ConnectionTable`
   (коллизии портов), `ProcessResolver` (кэш/TTL), `DecideFlow` (все ветки
   PROXY/DIRECT/BLOCK) с моками. Интегрировать существующий

7. **CI (низкий).** Добавить пайплайн: `msbuild` службы + `dotnet build` GUI +
   запуск `RuleEngineTest` на каждый коммит (сборка сейчас проходит «из
   коробки», что упрощает автоматизацию).
8. **Чистка репозитория (низкий).** Удалить реликты (п. 3.12), определиться с
   HookDLL/WFP (п. 3.13), навести порядок в каталогах деплоя (п. 3.11).
9. **Архитектура (низкий).** Убрать или задействовать `CompositionRoot`

## 6. Что проверить в рантайме (ручной чек-лист)

> Автоматический рантайм-тест в окружении аудита невозможен. Ниже — минимальный
> сценарий ручной проверки на реальном стенде (Windows, права администратора).

### Общее (для всех режимов)
- [ ] Служба устанавливается (`TcpRedirectorService.exe --install`) и стартует
      через SCM без перехода в STOPPED.
- [ ] Рядом с EXE появляется каталог **`.logs\`** (с точкой), в нём —
      `tcp_redirector.log`.
- [ ] **Ротация:** при достижении порога (по умолчанию 50 МБ, поле
      `log.maxSizeMB`) активный лог переименовывается в архив вида
      `tcp_redirector.YYYYMMDD_HHMMSS.log`, создаётся новый активный.
- [ ] **Retention:** архивы старше 24 ч и/или суммарно > 500 МБ удаляются
      (можно проверить, подложив «старые» файлы с изменённым временем).
- [ ] GUI подключается к службе и отображает статус/статистику.
- [ ] Остановка службы проходит без зависаний и без падения (порядок
      capture → pipe → relay → table).

### WinDivert (`capture_mode=windivert`)
- [ ] `WinDivert.dll` и `WinDivert64.sys` лежат рядом с EXE; preflight проходит.
- [ ] Трафик целевого приложения (по правилам `apps[]`) идёт через прокси;
      прочий — напрямую (DIRECT); правила BLOCK разрывают соединение.
- [ ] Отладочный `windivert_debug.log` пишется в **`.logs\`** (не в
      `%ProgramData%`).
- [ ] Смена правил через GUI подхватывается.

### Wintun embedded (`wintun.engine=embedded`)
- [ ] `wintun.dll` присутствует; адаптер `TcpRedirector` создаётся; назначается
      IPv4 из `tunnel_ipv4_cidr`; split-tunnel маршруты (0.0.0.0/1 + 128.0.0.0/1)
      ставятся и снимаются при остановке.
- [ ] **Фильтрация по процессу (Задача 2):** при `process_filter_enabled=true`
      соединения приложений из `apps[]` идут через прокси (PROXY), не подпадающие
      — напрямую (DIRECT), правила BLOCK отклоняются (`tcp_abort`).
- [ ] При `process_filter_enabled=false` — весь IPv4-TCP идёт через прокси
      (поведение Option 2b).
- [ ] Проверить поведение под нагрузкой (много одновременных новых соединений)
      на предмет латентности accept'а (см. п. 3.1).
- [ ] Убедиться, что «быстрые» приложения не уходят ложно в DIRECT (см. п. 3.2).

### Wintun external (`wintun.engine=external`)
- [ ] `.bin\tun2socks\tun2socks.exe` присутствует; SOCKS5-listener на
      `socks5_listen` поднимается; дочерний процесс стартует.
- [ ] Трафик туннеля проксируется через SOCKS5 → HTTP-прокси.
- [ ] При `process_filter_enabled=true` в лог выдаётся предупреждение об
      отсутствии пер-процессной фильтрации; трафик всё равно проксируется.
- [ ] **Устойчивость супервизора:** принудительно убить `tun2socks.exe` — при
      `restart_on_crash=true` он перезапускается с backoff; при остановке службы
      дочерний процесс гарантированно завершается (Job Object), сирот не остаётся.
