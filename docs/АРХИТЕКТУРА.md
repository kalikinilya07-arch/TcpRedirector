# Архитектура TcpRedirector

Документ описывает внутреннее устройство TcpRedirector: из каких компонентов состоит система, как они взаимодействуют и как трафик проходит путь от целевого приложения до вышестоящего прокси в каждом из трёх режимов работы.

Проект придерживается принципов гексагональной архитектуры (ports & adapters): доменная логика (`domain/`) отделена от инфраструктурных реализаций (`infrastructure/`) и адаптеров ввода/вывода (`adapters/`).

---

## 1. Компоненты

### 1.1. Служба (`TcpRedirectorService.exe`)

Ядро продукта — фоновая служба Windows. Исходники — в `src/service/TcpRedirectorService/`. Точка входа — [`main.cpp`](../src/service/TcpRedirectorService/main.cpp:68), которая либо регистрирует службу в SCM, либо (при запуске с флагом `--console`) работает как обычный процесс.

Логику старта/останова инкапсулирует класс `TcpRedirectorService` из [`ServiceMain.h`](../src/service/TcpRedirectorService/adapters/driving/ServiceMain.h:31). Его метод `Initialize()` последовательно:

1. Выполняет однократную миграцию `config.json` из `%ProgramData%` (см. §5).
2. Создаёт каталог логов `<exeDir>\logs\` и инициализирует логгер.
3. Загружает конфигурацию через `ConfigManager`.
4. Поднимает `RuleEngine` (правила сопоставления) и `ConnectionTracker` (учёт соединений).
5. Создаёт `ConnectionTable` (таблица «оригинальных назначений») и запускает `TcpRelayServer`.
6. Выполняет **preflight-проверку активного режима** (см. §4).
7. Создаёт нужную реализацию `ICapture` (WinDivert или Wintun) и открывает её.
8. Запускает IPC-сервер для связи с GUI.

### 1.2. Графический интерфейс (`TcpRedirectorGUI.exe`)

WPF-приложение на .NET (`src/gui/TcpRedirectorGUI/`), собираемое как self-contained. Позволяет редактировать правила, параметры прокси и авторизации, переключать режим захвата и наблюдать статистику. GUI **не** перехватывает трафик — он только редактирует `config.json` и общается со службой по IPC. Файл конфигурации GUI и служба используют один и тот же: GUI устанавливается в подкаталог `gui\`, а `config.json` лежит на уровень выше — рядом со службой.

### 1.3. Локальный relay (`TcpRelayServer`)

Реализация — [`TcpRelayServer.h`](../src/service/TcpRedirectorService/infrastructure/relay/TcpRelayServer.h:45). Это локальный TCP-сервер, слушающий `INADDR_ANY:34010` (порт `34010` задан в коде службы). Именно сюда оба режима захвата приводят перехваченные соединения. Relay:

- принимает входящее (перенаправленное) соединение;
- определяет **оригинальное назначение** соединения через `ConnectionTable`;
- устанавливает соединение с вышестоящим HTTP-прокси и отправляет запрос `CONNECT host:port`;
- при необходимости выполняет авторизацию (Basic или Kerberos/Negotiate через SSPI, см. [`auth_sspi.h`](../src/service/TcpRedirectorService/infrastructure/auth/auth_sspi.h:1));
- после успешного `CONNECT` запускает двунаправленный мост данных (client ↔ proxy).

Дополнительно relay может поднять **SOCKS5-слушатель** (`Socks5Adapter`) — он нужен только для внешнего движка Wintun (`engine=external`), чтобы `tun2socks.exe` мог форвардить туда потоки.

### 1.4. Абстракция захвата — `ICapture`

Доменный порт [`ICapture.h`](../src/service/TcpRedirectorService/domain/ports/ICapture.h:1) — единый контракт для механизма перехвата. Реализации:

- `WinDivertCapture` ([`WinDivertCapture.h`](../src/service/TcpRedirectorService/infrastructure/capture/WinDivertCapture.h:1)) — режим WinDivert;
- `WintunCapture` ([`WintunCapture.h`](../src/service/TcpRedirectorService/infrastructure/capture/WintunCapture.h:72)) — режим Wintun.

`ServiceMain` работает с захватом через базовый указатель `ICapture`, вызывая единообразно `Open()`, `Close()`, `SetConnectionTable()`, `SetRelayPort()`, `SetProxyConfig()`, `SetRuleEngine()`, а также геттеры статистики (RX/TX-байты, активные соединения).

### 1.5. Движки Wintun (`ITunEngine`)

Внутри `WintunCapture` работает один из движков, реализующих порт [`ITunEngine.h`](../src/service/TcpRedirectorService/infrastructure/capture/wintun/ITunEngine.h:1):

- **`Tun2SocksEngineEmbedded`** ([`.cpp`](../src/service/TcpRedirectorService/infrastructure/capture/wintun/Tun2SocksEngineEmbedded.cpp:1)) — встроенный TCP/IP-стек **lwIP**: принимает TCP-потоки прямо из TUN-адаптера и как loopback-клиент форвардит их на relay (`127.0.0.1:34010`). При включённой **фильтрации по процессу** (`wintun.process_filter_enabled`, по умолчанию `true`) в момент accept'а движок резолвит процесс-источник по source-порту и применяет те же `apps[]`-правила `RuleEngine`, что и WinDivert (PROXY/DIRECT/BLOCK); при DIRECT открывает прямой outbound на реальный dst, минуя прокси, при BLOCK — отклоняет соединение.
- **`Tun2SocksEngineExternal`** ([`.cpp`](../src/service/TcpRedirectorService/infrastructure/capture/wintun/Tun2SocksEngineExternal.cpp:1)) — запускает внешний `tun2socks.exe` под управлением `ChildProcessSupervisor` ([`.h`](../src/service/TcpRedirectorService/infrastructure/process/ChildProcessSupervisor.h:1)); внешний процесс форвардит потоки на локальный SOCKS5-слушатель relay. Фильтрация по процессу в этом режиме **не поддерживается** (см. §3.3).

Wintun-адаптер поднимают вспомогательные классы: `WintunApi` (загрузка `wintun.dll`), `WintunAdapter` (создание/открытие адаптера, назначение IPv4), `WintunSession` (сессия чтения/записи пакетов), `RouteInstaller` (установка split-tunnel маршрутов `0.0.0.0/1` и `128.0.0.0/1`). Определение процесса-источника по локальному TCP-порту инкапсулировано в `ProcessResolver` ([`.h`](../src/service/TcpRedirectorService/infrastructure/process/ProcessResolver.h:1)) — общий переиспользуемый компонент (PID-кэш поверх `GetExtendedTcpTable`, путь процесса, обход дерева процессов).

### 1.6. IPC (TCP loopback + токен-аутентификация)

Связь GUI ↔ служба реализована через IPC-сервер [`TcpIpcServer.h`](../src/service/TcpRedirectorService/infrastructure/ipc/TcpIpcServer.h:1) на `127.0.0.1:34011` (протокол — построчный JSON). В кодовой базе также присутствует альтернативная реализация именованного канала [`PipeServer.h`](../src/service/TcpRedirectorService/infrastructure/ipc/PipeServer.h:1) (не используется). Запросы обрабатывает [`IpcHandler`](../src/service/TcpRedirectorService/adapters/driving/IpcHandler.h:1): отдаёт GUI статистику, состояние службы и принимает команды (`set_config`, `set_rules`, `set_log_level`).

**Аутентификация (QA-аудит B1).** Канал слушает только loopback, а также защищён **per-run токеном**:

1. При старте служба генерирует случайный 256-битный токен (`CryptGenRandom`) и пишет его в `<exeDir>\.ipc_token` с DACL `D:P(A;;FA;;;BA)(A;;FA;;;SY)` — читать/писать могут только **Administrators** и **LOCAL_SYSTEM**.
2. GUI (запускается с правами администратора) читает токен из этого файла рядом с `config.json` и добавляет поле `token` в **каждый** IPC-запрос.
3. Служба отклоняет запросы без корректного токена (`{"status":"error","error":"unauthorized"}`), поэтому непривилегированный локальный процесс не может управлять службой.

> **Fail-safe.** Если токен не удалось сгенерировать/записать (напр. проблема ФС), служба логирует предупреждение и **не** навязывает аутентификацию — это не «кирпичит» единственный канал управления. Файл `.ipc_token` пересоздаётся при каждом старте; GUI перечитывает его при каждом переподключении.

**Пароль прокси через IPC (QA-аудит B4).** Поскольку GUI не может зашифровать секрет под учётной записью службы (DPAPI привязан к аккаунту), пароль Basic-auth передаётся службе в открытом виде по этому (аутентифицированному) каналу, а служба шифрует его через DPAPI и сохраняет в `config.json` (`auth.encryptedPassword`).

### 1.7. Конфигурация

`ConfigManager` ([`.h`](../src/service/TcpRedirectorService/infrastructure/config/ConfigManager.h:1) / [`.cpp`](../src/service/TcpRedirectorService/infrastructure/config/ConfigManager.cpp:1)) читает и пишет `config.json` (схема v2, структуры описаны в [`Config.h`](../src/service/TcpRedirectorService/infrastructure/config/Config.h:1)). Пути ресурсов резолвятся через [`AppPaths.h`](../src/service/TcpRedirectorService/infrastructure/paths/AppPaths.h:1) относительно каталога EXE. Пароль прокси хранится зашифрованным через **DPAPI** (Base64).

### 1.8. Логирование и статистика

- **Логирование:** [`Logger.h`](../src/service/TcpRedirectorService/infrastructure/logging/Logger.h:1) пишет в `<exeDir>\logs\` с уровнями ERROR/WARN/INFO/DEBUG и ротацией по размеру.
- **Статистика:** [`StatsCollector.h`](../src/service/TcpRedirectorService/infrastructure/stats/StatsCollector.h:1) и `ConnectionTracker` собирают счётчики байтов и активных соединений для показа в GUI.

## 2. Восстановление оригинального назначения

Ключевая задача любого прозрачного проксирования — узнать, **куда** приложение хотело подключиться, ведь трафик уже перенаправлен на локальный relay.

- **Режим WinDivert:** служба перехватывает исходящий TCP-SYN, запоминает пару (порт источника → оригинальный `dst_ip:dst_port`) в `ConnectionTable`, затем подменяет назначение пакета на `127.0.0.1:34010`. Когда relay принимает соединение, он ищет в `ConnectionTable` запись по параметрам сокета и восстанавливает оригинальное назначение.
- **Режим Wintun:** весь IPv4-TCP уходит в TUN-адаптер. Движок (lwIP или `tun2socks`) терминирует TCP-поток и знает исходный `dst_ip:dst_port` из IP/TCP-заголовков пакета. Он передаёт эту информацию на relay (напрямую или через SOCKS5), где также используется `ConnectionTable`/протокол SOCKS5 для восстановления адреса. В embedded-варианте перед форвардингом применяется **фильтрация по процессу** (см. §3.2): проксируется только трафик приложений, сматчившихся с `apps[]`; остальное уходит напрямую.

Далее relay в обоих случаях делает `CONNECT host:port` к вышестоящему прокси и мостит данные.

## 3. Потоки данных по режимам

Общий финал одинаков для всех режимов:

```
… → TcpRelayServer(127.0.0.1:34010) → HTTP CONNECT (+Basic/Kerberos) → вышестоящий прокси → адресат
```

### 3.1. Режим WinDivert

```
┌─────────────────┐     исходящий SYN на real_dst      ┌──────────────────────┐
│ Целевое         │  ───────────────────────────────▶ │ WinDivertCapture      │
│ приложение      │                                     │ (перехват SYN)        │
└─────────────────┘                                     └──────────┬───────────┘
                                                                    │ 1) запомнить real_dst
                                                                    │    в ConnectionTable
                                                                    │ 2) подменить dst →
                                                                    │    127.0.0.1:34010
                                                                    ▼
                                                         ┌──────────────────────┐
                                                         │ TcpRelayServer        │
                                                         │ :34010                │
                                                         │ - lookup real_dst     │
                                                         │ - CONNECT к прокси    │
                                                         │ - Basic/Kerberos auth │
                                                         └──────────┬───────────┘
                                                                    ▼
                                                         ┌──────────────────────┐
                                                         │ Вышестоящий HTTP-прокси│
                                                         └──────────┬───────────┘
                                                                    ▼
                                                              real_dst (адресат)
```

Фильтрация по процессам и портам выполняется `RuleEngine`: перехватываются только SYN тех процессов и портов, что подходят под `apps[]`.

### 3.2. Режим Wintun + embedded (lwIP)

```
┌─────────────────┐   IPv4-TCP согласно split-route    ┌──────────────────────┐
│ Целевое         │   (0.0.0.0/1 + 128.0.0.0/1)        │ Wintun TUN-адаптер     │
│ приложение      │  ───────────────────────────────▶ │ "TcpRedirector"        │
└─────────────────┘                                     └──────────┬───────────┘
                                                                    │ пакеты через WintunSession
                                                                    ▼
                                                         ┌──────────────────────┐
                                                         │ Tun2SocksEngineEmbedded│
                                                         │ (стек lwIP в службе)   │
                                                         │ - терминирует TCP      │
                                                         │ - знает real_dst из IP │
                                                         └──────────┬───────────┘
                                                                    │ loopback TCP-клиент
                                                                    ▼
                                                         ┌──────────────────────┐
                                                         │ TcpRelayServer :34010  │
                                                         │ - CONNECT к прокси     │
                                                         │ - Basic/Kerberos auth  │
                                                         └──────────┬───────────┘
                                                                    ▼
                                                              вышестоящий прокси → адресат
```

Внешних процессов нет — весь стек работает внутри службы. SOCKS5-слушатель relay в этом режиме **не** активируется.

**Фильтрация по процессу (Задача 2).** При `wintun.process_filter_enabled=true` (по умолчанию) в момент приёма каждого TCP-соединения из туннеля движок `Tun2SocksEngineEmbedded`:
1. резолвит PID процесса-источника по локальному (source) порту через `ProcessResolver` (`GetExtendedTcpTable`, PID-кэш TTL 30 c, один ретрай 20 мс при промахе);
2. получает путь процесса и спрашивает `RuleEngine` (`MatchForFlow` → legacy `Match` → fallback по `app.exePath`/дереву процессов) — ту же логику, что и `WinDivertCapture::CheckProcessRule`;
3. применяет решение: **PROXY** → форвард на relay (как на схеме выше); **DIRECT** → прямой outbound-сокет на реальный `dst_ip:dst_port`, минуя прокси; **BLOCK** → `tcp_abort`.

Так поведение фильтрации становится консистентным между режимами WinDivert и Wintun (embedded). При `process_filter_enabled=false` весь IPv4-TCP проксируется без разбора процесса (прежнее поведение Option 2b).

### 3.3. Режим Wintun + external (tun2socks.exe)

```
┌─────────────────┐   IPv4-TCP согласно split-route    ┌──────────────────────┐
│ Целевое         │   (0.0.0.0/1 + 128.0.0.0/1)        │ Wintun TUN-адаптер     │
│ приложение      │  ───────────────────────────────▶ │ "TcpRedirector"        │
└─────────────────┘                                     └──────────┬───────────┘
                                                                    ▼
                                                         ┌──────────────────────┐
                                                         │ tun2socks.exe          │
                                                         │ (внешний процесс,      │
                                                         │  ChildProcessSupervisor│
                                                         │  + авто-рестарт)       │
                                                         └──────────┬───────────┘
                                                                    │ SOCKS5 → socks5_listen
                                                                    │ (напр. 127.0.0.1:1080)
                                                                    ▼
                                                         ┌──────────────────────┐
                                                         │ TcpRelayServer         │
                                                         │ SOCKS5-слушатель       │
                                                         │ + :34010               │
                                                         │ - CONNECT к прокси     │
                                                         │ - Basic/Kerberos auth  │
                                                         └──────────┬───────────┘
                                                                    ▼
                                                              вышестоящий прокси → адресат
```

Перед стартом захвата служба поднимает SOCKS5-слушатель relay на адресе из `wintun.external_engine.socks5_listen`, затем запускает `tun2socks.exe`. Дочерний процесс контролируется супервизором; при падении — авто-рестарт с задержкой `restart_backoff_ms` (если `restart_on_crash=true`).

**Ограничение фильтрации по процессу.** В external-режиме фильтрация по конкретному процессу на уровне отдельного соединения **невозможна**: трафик терминирует дочерний `tun2socks.exe`, а на границе SOCKS5 источником любого соединения является сам `tun2socks.exe` (его PID), а не оригинальное приложение (source-порт исходного приложения при этом не сохраняется). Поэтому `wintun.process_filter_enabled` в этом режиме игнорируется — весь трафик туннеля проксируется (при `true` в лог пишется предупреждение). Для фильтрации по процессу используйте embedded-движок или режим WinDivert.

## 4. Preflight — проверка зависимостей активного режима

Перед созданием захвата `ServiceMain` выполняет **preflight** только для активного режима (см. [`ServiceMain.h`](../src/service/TcpRedirectorService/adapters/driving/ServiceMain.h:168)). Файлы неактивного режима не проверяются — это принципиально: WinDivert-развёртывание не требует `wintun.dll`, и наоборот.

- **`WinDivertPreflight`** ([`.h`](../src/service/TcpRedirectorService/infrastructure/preflight/WinDivertPreflight.h:39)) — проверяет наличие `WinDivert.dll` и `WinDivert64.sys` рядом с EXE, права администратора; версию DLL проверяет как «мягкое» предупреждение.
- **`WintunPreflight`** ([`.h`](../src/service/TcpRedirectorService/infrastructure/preflight/WintunPreflight.h:44)) — проверяет каталог `.bin\`, наличие и загружаемость `.bin\wintun\x64\wintun.dll`, права администратора, непустое `adapter_name`, корректный `tunnel_ipv4_cidr`; при `engine=external` дополнительно проверяет существование `tun2socks.exe` и корректность `socks5_listen`.

При обнаружении блокирующих ошибок (`failures`) служба логирует их и **отказывается стартовать** (остаётся в состоянии Stopped). Подробности — в [`docs/ПЕРЕКЛЮЧЕНИЕ_РЕЖИМА.md`](ПЕРЕКЛЮЧЕНИЕ_РЕЖИМА.md).

## 5. Расположение конфигурации и миграция

Все ресурсы службы резолвятся относительно каталога EXE (через `GetModuleFileNameW`, см. [`AppPaths.h`](../src/service/TcpRedirectorService/infrastructure/paths/AppPaths.h:37)) — это единственный надёжный способ, поскольку под SCM рабочий каталог службы равен `System32`.

- `config.json` — `<exeDir>\config.json`;
- логи — `<exeDir>\logs\`;
- внешние бинарники — `<exeDir>\.bin\`.

При старте служба выполняет **однократную миграцию** legacy-конфига: если `<exeDir>\config.json` отсутствует, но существует `%ProgramData%\TcpRedirector\config.json`, файл копируется рядом с EXE (см. `EnsureConfigMigrated()` в [`ConfigManager.cpp`](../src/service/TcpRedirectorService/infrastructure/config/ConfigManager.cpp:47)). Если новый файл уже есть, миграция пропускается.

## 6. Модель схемы конфигурации (v2)

Структуры конфигурации (`Config`, `WintunSettings`, `ExternalEngineSettings`, `AppRule`, `PortRange` и др.) определены в [`Config.h`](../src/service/TcpRedirectorService/infrastructure/config/Config.h:1). Схема помечена полем `config_version = 2`; конфиги без этого маркера считаются v1 и «на лету» преобразуются в v2 (legacy `rules[]` → `apps[]`). Полное описание всех полей — в [`docs/КОНФИГУРАЦИЯ.md`](КОНФИГУРАЦИЯ.md).
