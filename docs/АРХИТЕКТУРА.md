# Архитектура TcpRedirector

Документ описывает внутреннее устройство TcpRedirector: из каких компонентов состоит система, как они взаимодействуют и как трафик проходит путь от целевого приложения до вышестоящего прокси в каждом из трёх режимов работы.

Проект придерживается принципов гексагональной архитектуры (ports & adapters): доменная логика (`domain/`) отделена от инфраструктурных реализаций (`infrastructure/`) и адаптеров ввода/вывода (`adapters/`).

---

## 1. Компоненты

### 1.1. Служба (`TcpRedirectorService.exe`)

Ядро продукта — фоновая служба Windows. Исходники — в `src/service/TcpRedirectorService/`. Точка входа — [`main.cpp`](../src/service/TcpRedirectorService/main.cpp:68), которая либо регистрирует службу в SCM, либо (при запуске с флагом `--console`) работает как обычный процесс.

Логику старта/останова инкапсулирует класс `TcpRedirectorService` из [`ServiceMain.h`](../src/service/TcpRedirectorService/adapters/driving/ServiceMain.h:31). Его метод `Initialize()` последовательно:

1. Выполняет однократную миграцию `config.json` из `%ProgramData%` (см. §5).
2. Создаёт каталог логов `<exeDir>\logs\` и инициализирует логгер.
3. Загружает конфигурацию через `ConfigManager`.
4. Поднимает `RuleEngine` (правила сопоставления) и `ConnectionTracker` (учёт соединений).
5. Создаёт `ConnectionTable` (таблица «оригинальных назначений») и запускает `TcpRelayServer`.
6. Выполняет **preflight-проверку активного режима** (см. §4).
7. Создаёт нужную реализацию `ICapture` (WinDivert или Wintun) и открывает её.
8. Запускает IPC-сервер для связи с GUI.

### 1.2. Графический интерфейс (`TcpRedirectorGUI.exe`)

WPF-приложение на .NET (`src/gui/TcpRedirectorGUI/`), собираемое как self-contained. Позволяет редактировать правила, параметры прокси и авторизации, переключать режим захвата и наблюдать статистику. GUI **не** перехватывает трафик — он только редактирует `config.json` и общается со службой по IPC. Файл конфигурации GUI и служба используют один и тот же: GUI устанавливается в подкаталог `gui\`, а `config.json` лежит на уровень выше — рядом со службой.

**Управление службой (старт/стоп).** GUI использует **единую авторитетную модель** на основе реального состояния службы в SCM ([`ServiceController.cs`](../src/gui/TcpRedirectorGUI/Infrastructure/Scm/ServiceController.cs:1), [`ShellViewModel.cs`](../src/gui/TcpRedirectorGUI/Adapters/Driving/Wpf/ViewModels/ShellViewModel.cs:1)):

- **Установленная служба** управляется через SCM: старт — `ServiceController.Start()` + `WaitForStatus(Running, 15 c)` (без появления консольного окна); стоп — `ServiceController.Stop()` + `WaitForStatus(Stopped, 15 c)`. Чистый SCM-стоп рапортует `SERVICE_STOPPED` (exit 0), поэтому **не** триггерит SCM failure/recovery actions (см. §1.1 и `ИЗВЕСТНЫЕ_ПРОБЛЕМЫ.md` B16) — служба не перезапускается после остановки из GUI.
- **Неустановленная служба** (dev/переносной запуск) запускается GUI как **безоконный** процесс (`UseShellExecute=false`, `CreateNoWindow=true`, `WindowStyle=Hidden`) и останавливается его завершением — это безопасно, т.к. SCM-регистрации (и failure actions) нет.

> Прежняя модель всегда запускала дочерний `--console`-процесс (видимое консольное окно) и «останавливала» его `Kill()`, что SCM трактовал как сбой и перезапускал службу по failure actions. Оба симптома устранены (см. `ИЗВЕСТНЫЕ_ПРОБЛЕМЫ.md` §0.9, B17).

### 1.3. Локальный relay (`TcpRelayServer`)

Реализация — [`TcpRelayServer.h`](../src/service/TcpRedirectorService/infrastructure/relay/TcpRelayServer.h:45). Это локальный TCP-сервер, слушающий `INADDR_ANY:34010` (порт `34010` задан в коде службы). Именно сюда оба режима захвата приводят перехваченные соединения. Relay:

- принимает входящее (перенаправленное) соединение;
- определяет **оригинальное назначение** соединения через `ConnectionTable`;
- устанавливает соединение с вышестоящим HTTP-прокси и отправляет запрос `CONNECT host:port`;
- при необходимости выполняет авторизацию (Basic или Kerberos/Negotiate через SSPI, см. [`auth_sspi.h`](../src/service/TcpRedirectorService/infrastructure/auth/auth_sspi.h:1));
- после успешного `CONNECT` запускает двунаправленный мост данных (client ↔ proxy).

Дополнительно relay может поднять **SOCKS5-слушатель** (`Socks5Adapter`) — он нужен только для внешнего движка Wintun (`engine=external`), чтобы `tun2socks.exe` мог форвардить туда потоки.

### 1.4. Абстракция захвата — `ICapture`

Доменный порт [`ICapture.h`](../src/service/TcpRedirectorService/domain/ports/ICapture.h:1) — единый контракт для механизма перехвата. Реализации:

- `WinDivertCapture` ([`WinDivertCapture.h`](../src/service/TcpRedirectorService/infrastructure/capture/WinDivertCapture.h:1)) — режим WinDivert;
- `WintunCapture` ([`WintunCapture.h`](../src/service/TcpRedirectorService/infrastructure/capture/WintunCapture.h:72)) — режим Wintun.

`ServiceMain` работает с захватом через базовый указатель `ICapture`, вызывая единообразно `Open()`, `Close()`, `SetConnectionTable()`, `SetRelayPort()`, `SetProxyConfig()`, `SetRuleEngine()`, а также геттеры статистики (RX/TX-байты, активные соединения).

### 1.5. Движки Wintun (`ITunEngine`)

Внутри `WintunCapture` работает один из движков, реализующих порт [`ITunEngine.h`](../src/service/TcpRedirectorService/infrastructure/capture/wintun/ITunEngine.h:1):

- **`Tun2SocksEngineEmbedded`** ([`.cpp`](../src/service/TcpRedirectorService/infrastructure/capture/wintun/Tun2SocksEngineEmbedded.cpp:1)) — встроенный TCP/IP-стек **lwIP**: принимает TCP-потоки прямо из TUN-адаптера и как loopback-клиент форвардит их на relay (`127.0.0.1:34010`). При включённой **фильтрации по процессу** (`wintun.process_filter_enabled`, по умолчанию `true`) в момент accept'а движок резолвит процесс-источник по source-порту и применяет те же `apps[]`-правила `RuleEngine`, что и WinDivert. Для PROXY-решения движок регистрирует `(эфемерный порт loopback-сокета → original-dst)` в `ConnectionTable`, чтобы relay мог восстановить адрес назначения. **BLOCK** в embedded отклоняется (`tcp_abort`). Поведение **DIRECT** (не-совпавший трафик) зависит от `wintun.direct_passthrough` (Задача 3): по умолчанию (`false`) DIRECT-flow отклоняется (`tcp_abort`, прежнее поведение), а при `true` embedded пропускает такой трафик **напрямую** мимо прокси через физический интерфейс (async-outbound + `IP_UNICAST_IF`, см. §3.2). Для «проксировать всё» используйте `process_filter_enabled=false`; для прямого прохода не-целевого трафика — `direct_passthrough=true` (или `capture_mode=windivert`).
- **`Tun2SocksEngineExternal`** ([`.cpp`](../src/service/TcpRedirectorService/infrastructure/capture/wintun/Tun2SocksEngineExternal.cpp:1)) — запускает внешний `tun2socks.exe` под управлением `ChildProcessSupervisor` ([`.h`](../src/service/TcpRedirectorService/infrastructure/process/ChildProcessSupervisor.h:1)); внешний процесс форвардит потоки на локальный SOCKS5-слушатель relay. Фильтрация по процессу в этом режиме **не поддерживается** (см. §3.3).

Wintun-адаптер поднимают вспомогательные классы: `WintunApi` (загрузка `wintun.dll`), `WintunAdapter` (создание/открытие адаптера, назначение IPv4), `WintunSession` (сессия чтения/записи пакетов), `RouteInstaller` (установка split-tunnel маршрутов `0.0.0.0/1` и `128.0.0.0/1`). Определение процесса-источника по локальному TCP-порту инкапсулировано в `ProcessResolver` ([`.h`](../src/service/TcpRedirectorService/infrastructure/process/ProcessResolver.h:1)) — общий переиспользуемый компонент (PID-кэш поверх `GetExtendedTcpTable`, путь процесса, обход дерева процессов).

### 1.6. IPC (TCP loopback + токен-аутентификация)

Связь GUI ↔ служба реализована через IPC-сервер [`TcpIpcServer.h`](../src/service/TcpRedirectorService/infrastructure/ipc/TcpIpcServer.h:1) на `127.0.0.1:34011` (протокол — построчный JSON). В кодовой базе также присутствует альтернативная реализация именованного канала [`PipeServer.h`](../src/service/TcpRedirectorService/infrastructure/ipc/PipeServer.h:1) (не используется). Запросы обрабатывает [`IpcHandler`](../src/service/TcpRedirectorService/adapters/driving/IpcHandler.h:1): отдаёт GUI статистику, состояние службы и принимает команды (`set_config`, `set_rules`, `set_log_level`).

**Ответ `service_status` и поле `auth_status` (Задача 2).** В ответ со статусом службы добавлено строковое поле **`auth_status`** — health-статус подсистемы per-user Kerberos (`AuthHelperManager`), который GUI показывает **вторым** индикатором (см. §7 и раздел GUI в [`docs/УСТАНОВКА.md`](УСТАНОВКА.md)). Значения:

| `auth_status` | Смысл |
|---------------|-------|
| `disabled` | Per-user Kerberos не включён (`AuthHelperManager` отсутствует) |
| `active` | Менеджер работает, есть ≥1 живой helper-процесс |
| `no_helper` | Функция включена, но живого helper'а нет (нет интерактивной сессии / запуск не удался) |
| `error` | Менеджер не смог стартовать / не запущен при включённой функции |

Поле формирует служба ([`ServiceMain.h`](../src/service/TcpRedirectorService/adapters/driving/ServiceMain.h:1) → [`IpcHandler.h`](../src/service/TcpRedirectorService/adapters/driving/IpcHandler.h:1) на основе [`AuthHelperManager`](../src/service/TcpRedirectorService/infrastructure/auth/AuthHelperManager.h:1)); GUI читает его в [`IpcClient.cs`](../src/gui/TcpRedirectorGUI/Infrastructure/Ipc/IpcClient.cs:1) и мапит в [`ProxyConfig.cs`](../src/gui/TcpRedirectorGUI/Domain/Entities/ProxyConfig.cs:1)/[`ShellViewModel.cs`](../src/gui/TcpRedirectorGUI/Adapters/Driving/Wpf/ViewModels/ShellViewModel.cs:1).

**Аутентификация (QA-аудит B1).** Канал слушает только loopback, а также защищён **per-run токеном**:

1. При старте служба генерирует случайный 256-битный токен (`CryptGenRandom`) и пишет его в `<exeDir>\.ipc_token` с DACL `D:P(A;;FA;;;BA)(A;;FA;;;SY)` — читать/писать могут только **Administrators** и **LOCAL_SYSTEM**.
2. GUI (запускается с правами администратора) читает токен из этого файла рядом с `config.json` и добавляет поле `token` в **каждый** IPC-запрос.
3. Служба отклоняет запросы без корректного токена (`{"status":"error","error":"unauthorized"}`), поэтому непривилегированный локальный процесс не может управлять службой.

> **Fail-safe.** Если токен не удалось сгенерировать/записать (напр. проблема ФС), служба логирует предупреждение и **не** навязывает аутентификацию — это не «кирпичит» единственный канал управления. Файл `.ipc_token` пересоздаётся при каждом старте; GUI перечитывает его при каждом переподключении.

**Пароль прокси через IPC (QA-аудит B4).** Поскольку GUI не может зашифровать секрет под учётной записью службы (DPAPI привязан к аккаунту), пароль Basic-auth передаётся службе в открытом виде по этому (аутентифицированному) каналу, а служба шифрует его через DPAPI и сохраняет в `config.json` (`auth.encryptedPassword`).

### 1.7. Конфигурация

`ConfigManager` ([`.h`](../src/service/TcpRedirectorService/infrastructure/config/ConfigManager.h:1) / [`.cpp`](../src/service/TcpRedirectorService/infrastructure/config/ConfigManager.cpp:1)) читает и пишет `config.json` (схема v2, структуры описаны в [`Config.h`](../src/service/TcpRedirectorService/infrastructure/config/Config.h:1)). Пути ресурсов резолвятся через [`AppPaths.h`](../src/service/TcpRedirectorService/infrastructure/paths/AppPaths.h:1) относительно каталога EXE. Пароль прокси хранится зашифрованным через **DPAPI** (Base64).

### 1.8. Логирование и статистика

- **Логирование:** [`Logger.h`](../src/service/TcpRedirectorService/infrastructure/logging/Logger.h:1) пишет в `<exeDir>\logs\` с уровнями ERROR/WARN/INFO/DEBUG и ротацией по размеру.
- **Статистика:** [`StatsCollector.h`](../src/service/TcpRedirectorService/infrastructure/stats/StatsCollector.h:1) и `ConnectionTracker` собирают счётчики байтов и активных соединений для показа в GUI.

## 2. Восстановление оригинального назначения

Ключевая задача любого прозрачного проксирования — узнать, **куда** приложение хотело подключиться, ведь трафик уже перенаправлен на локальный relay.

- **Режим WinDivert:** служба перехватывает исходящий TCP-SYN, запоминает пару (порт источника → оригинальный `dst_ip:dst_port`) в `ConnectionTable`, затем подменяет назначение пакета на `127.0.0.1:34010`. Когда relay принимает соединение, он ищет в `ConnectionTable` запись по параметрам сокета и восстанавливает оригинальное назначение.
- **Режим Wintun:** весь IPv4-TCP уходит в TUN-адаптер. Движок (lwIP или `tun2socks`) терминирует TCP-поток и знает исходный `dst_ip:dst_port` из IP/TCP-заголовков пакета. Он передаёт эту информацию на relay через `ConnectionTable` (embedded регистрирует запись по эфемерному порту своего loopback-сокета к relay) либо через протокол SOCKS5 (external). В embedded-варианте перед форвардингом применяется **фильтрация по процессу** (см. §3.2): проксируется только трафик приложений, сматчившихся с `apps[]`; остальное (DIRECT) в embedded по умолчанию отклоняется, а при `wintun.direct_passthrough=true` — пропускается напрямую мимо прокси через физический интерфейс (см. §3.2).

Далее relay в обоих случаях делает `CONNECT host:port` к вышестоящему прокси и мостит данные.

## 3. Потоки данных по режимам

Общий финал одинаков для всех режимов:

```
… → TcpRelayServer(127.0.0.1:34010) → HTTP CONNECT (+Basic/Kerberos) → вышестоящий прокси → адресат
```

### 3.1. Режим WinDivert

```
┌─────────────────┐     исходящий SYN на real_dst      ┌──────────────────────┐
│ Целевое         │  ───────────────────────────────▶ │ WinDivertCapture      │
│ приложение      │                                     │ (перехват SYN)        │
└─────────────────┘                                     └──────────┬───────────┘
                                                                    │ 1) запомнить real_dst
                                                                    │    в ConnectionTable
                                                                    │ 2) подменить dst →
                                                                    │    127.0.0.1:34010
                                                                    ▼
                                                         ┌──────────────────────┐
                                                         │ TcpRelayServer        │
                                                         │ :34010                │
                                                         │ - lookup real_dst     │
                                                         │ - CONNECT к прокси    │
                                                         │ - Basic/Kerberos auth │
                                                         └──────────┬───────────┘
                                                                    ▼
                                                         ┌──────────────────────┐
                                                         │ Вышестоящий HTTP-прокси│
                                                         └──────────┬───────────┘
                                                                    ▼
                                                              real_dst (адресат)
```

Фильтрация по процессам и портам выполняется `RuleEngine`: перехватываются только SYN тех процессов и портов, что подходят под `apps[]`.

### 3.2. Режим Wintun + embedded (lwIP)

```
┌─────────────────┐   IPv4-TCP согласно split-route    ┌──────────────────────┐
│ Целевое         │   (0.0.0.0/1 + 128.0.0.0/1)        │ Wintun TUN-адаптер     │
│ приложение      │  ───────────────────────────────▶ │ "TcpRedirector"        │
└─────────────────┘                                     └──────────┬───────────┘
                                                                    │ пакеты через WintunSession
                                                                    ▼
                                                         ┌──────────────────────┐
                                                         │ Tun2SocksEngineEmbedded│
                                                         │ (стек lwIP в службе)   │
                                                         │ - терминирует TCP      │
                                                         │ - знает real_dst из IP │
                                                         └──────────┬───────────┘
                                                                    │ loopback TCP-клиент
                                                                    ▼
                                                         ┌──────────────────────┐
                                                         │ TcpRelayServer :34010  │
                                                         │ - CONNECT к прокси     │
                                                         │ - Basic/Kerberos auth  │
                                                         └──────────┬───────────┘
                                                                    ▼
                                                              вышестоящий прокси → адресат
```

Внешних процессов нет — весь стек работает внутри службы. SOCKS5-слушатель relay в этом режиме **не** активируется.

**Фильтрация по процессу (Задача 2).** При `wintun.process_filter_enabled=true` (по умолчанию) в момент приёма каждого TCP-соединения из туннеля движок `Tun2SocksEngineEmbedded`:
1. резолвит PID процесса-источника по локальному (source) порту через `ProcessResolver` (`GetExtendedTcpTable`, PID-кэш TTL 30 c, один ретрай 20 мс при промахе);
2. получает путь процесса и спрашивает `RuleEngine` (`MatchForFlow` → legacy `Match` → fallback по `app.exePath`/дереву процессов) — ту же логику, что и `WinDivertCapture::CheckProcessRule`;
3. применяет решение: **PROXY** → форвард на relay; **DIRECT** (не-совпавший трафик) → отклоняется (`tcp_abort`) **или** пропускается напрямую — зависит от `wintun.direct_passthrough` (см. ниже); **BLOCK** → `tcp_abort`.

**Восстановление original-dst для PROXY (важно).** Перед `connect()` к relay движок биндит loopback-сокет к `127.0.0.1:0`, узнаёт назначенный эфемерный порт и регистрирует `(этот_порт → original-dst)` в `ConnectionTable`. Relay при accept'е восстанавливает адрес назначения именно по этому порту (`ConnectionTable::Get`), как и для WinDivert/SOCKS5. Без этой записи relay не знает, куда подключаться, и закрывает соединение (`No connection record for port …`) — исторический баг «трафик виден, но не форвардится», исправлен.

**Прямой проход DIRECT в embedded (`wintun.direct_passthrough`, Задача 3).**

- **По умолчанию (`direct_passthrough=false`)** DIRECT-flow **отклоняется** (`tcp_abort`, fail-fast) — прежнее поведение. Причина, по которой прямой проход нельзя было делать «в лоб»: `OnAccept` выполняется на engine-треде, а блокирующий `connect()` к реальному dst ушёл бы по split-tunnel-маршрутам ОБРАТНО в тот же TUN — прочитать его некому (тот же тред занят `connect()`), и стек замерзает.
- **При `direct_passthrough=true`** embedded реализует сквозной прямой проход (Option 1 из [`plans/wintun_embedded_direct_passthrough_options.md`](../plans/wintun_embedded_direct_passthrough_options.md)), соблюдая два инварианта: **(1)** ни один вызов не блокирует engine-тред и **(2)** исходящие DIRECT-пакеты не заворачиваются обратно в TUN. Механизм:
  1. на DIRECT-решение движок открывает per-flow outbound-сокет к **реальному** `original-dst` (без регистрации в `ConnectionTable` — это шаг только для PROXY);
  2. сокет пиннится к **физическому** интерфейсу через `IP_UNICAST_IF` (индекс интерфейса из `GetBestRoute2`, в network byte order) + bind на source-IP физического NIC как fallback — так SYN выходит мимо TUN-лестницы;
  3. `connect()` и двунаправленная перекачка данных выполняются на **собственном треде flow'а** (`DirectFlowThread`), переиспользуя проверенную per-flow reader/reaper-машинерию — engine-тред возвращается из `OnAccept` немедленно;
  4. опционально поверх включается **Option 2a** — динамический `<dst>/32` bypass через физический шлюз (`wintun.direct_route_optimization`, по умолчанию `true`, когда passthrough включён): последующий трафик к тому же IP уходит мимо TUN уже на уровне ОС. Такой `/32` **никогда** не ставится для dst, используемого PROXY-приложением, и полностью снимается при закрытии flow'а и при `Stop()`.
- Если физический egress установить не удалось (не резолвится интерфейс/source-IP или `connect` провалился на настройке), действует `wintun.direct_fallback`: `drop` (по умолчанию, `tcp_abort`) или `proxy` (отправить через relay/прокси).
- Прямой проход **IPv4-only** (IPv6 по-прежнему нейтрализуется, см. §3.2 и `block_ipv6`). Это NAT-подобный проход: для DIRECT-соединения исходным адресом становится хост службы, а не приложение.

Диагностика в логе: `[wintun][flow] DIRECT …`, `[wintun][bypass] …`.

При `process_filter_enabled=false` весь IPv4-TCP проксируется без разбора процесса (поведение Option 2b) — DIRECT не возникает, и embedded форвардит весь трафик через relay/прокси.

### 3.3. Режим Wintun + external (tun2socks.exe)

```
┌─────────────────┐   IPv4-TCP согласно split-route    ┌──────────────────────┐
│ Целевое         │   (0.0.0.0/1 + 128.0.0.0/1)        │ Wintun TUN-адаптер     │
│ приложение      │  ───────────────────────────────▶ │ "TcpRedirector"        │
└─────────────────┘                                     └──────────┬───────────┘
                                                                    ▼
                                                         ┌──────────────────────┐
                                                         │ tun2socks.exe          │
                                                         │ (внешний процесс,      │
                                                         │  ChildProcessSupervisor│
                                                         │  + авто-рестарт)       │
                                                         └──────────┬───────────┘
                                                                    │ SOCKS5 → socks5_listen
                                                                    │ (напр. 127.0.0.1:1080)
                                                                    ▼
                                                         ┌──────────────────────┐
                                                         │ TcpRelayServer         │
                                                         │ SOCKS5-слушатель       │
                                                         │ + :34010               │
                                                         │ - CONNECT к прокси     │
                                                         │ - Basic/Kerberos auth  │
                                                         └──────────┬───────────┘
                                                                    ▼
                                                              вышестоящий прокси → адресат
```

Перед стартом захвата служба поднимает SOCKS5-слушатель relay на адресе из `wintun.external_engine.socks5_listen`, затем запускает `tun2socks.exe`. Дочерний процесс контролируется супервизором; при падении — авто-рестарт с задержкой `restart_backoff_ms` (если `restart_on_crash=true`).

**Ограничение фильтрации по процессу.** В external-режиме фильтрация по конкретному процессу на уровне отдельного соединения **невозможна**: трафик терминирует дочерний `tun2socks.exe`, а на границе SOCKS5 источником любого соединения является сам `tun2socks.exe` (его PID), а не оригинальное приложение (source-порт исходного приложения при этом не сохраняется). Поэтому `wintun.process_filter_enabled` в этом режиме игнорируется — весь трафик туннеля проксируется (при `true` в лог пишется предупреждение). Для фильтрации по процессу используйте embedded-движок или режим WinDivert.

## 4. Preflight — проверка зависимостей активного режима

Перед созданием захвата `ServiceMain` выполняет **preflight** только для активного режима (см. [`ServiceMain.h`](../src/service/TcpRedirectorService/adapters/driving/ServiceMain.h:168)). Файлы неактивного режима не проверяются — это принципиально: WinDivert-развёртывание не требует `wintun.dll`, и наоборот.

- **`WinDivertPreflight`** ([`.h`](../src/service/TcpRedirectorService/infrastructure/preflight/WinDivertPreflight.h:39)) — проверяет наличие `WinDivert.dll` и `WinDivert64.sys` рядом с EXE, права администратора; версию DLL проверяет как «мягкое» предупреждение.
- **`WintunPreflight`** ([`.h`](../src/service/TcpRedirectorService/infrastructure/preflight/WintunPreflight.h:44)) — проверяет каталог `.bin\`, наличие и загружаемость `.bin\wintun\x64\wintun.dll`, права администратора, непустое `adapter_name`, корректный `tunnel_ipv4_cidr`; при `engine=external` дополнительно проверяет существование `tun2socks.exe` и корректность `socks5_listen`.

При обнаружении блокирующих ошибок (`failures`) служба логирует их и **отказывается стартовать** (остаётся в состоянии Stopped). Подробности — в [`docs/ПЕРЕКЛЮЧЕНИЕ_РЕЖИМА.md`](ПЕРЕКЛЮЧЕНИЕ_РЕЖИМА.md).

## 5. Расположение конфигурации и миграция

Все ресурсы службы резолвятся относительно каталога EXE (через `GetModuleFileNameW`, см. [`AppPaths.h`](../src/service/TcpRedirectorService/infrastructure/paths/AppPaths.h:37)) — это единственный надёжный способ, поскольку под SCM рабочий каталог службы равен `System32`.

- `config.json` — `<exeDir>\config.json`;
- логи — `<exeDir>\logs\`;
- внешние бинарники — `<exeDir>\.bin\`.

При старте служба выполняет **однократную миграцию** legacy-конфига: если `<exeDir>\config.json` отсутствует, но существует `%ProgramData%\TcpRedirector\config.json`, файл копируется рядом с EXE (см. `EnsureConfigMigrated()` в [`ConfigManager.cpp`](../src/service/TcpRedirectorService/infrastructure/config/ConfigManager.cpp:47)). Если новый файл уже есть, миграция пропускается.

## 7. Per-user Kerberos-аутентификация (Variant 4b, опционально)

По умолчанию служба работает под `LocalSystem`, поэтому все SSPI/Negotiate-вызовы relay ([`auth_sspi.cpp`](../src/service/TcpRedirectorService/infrastructure/auth/auth_sspi.cpp:1), `AcquireCredentialsHandleW(NULL, L"Negotiate", …)`) выполняются под **машинным аккаунтом домена** (`COMPUTERNAME$`), а не под пользователем, запустившим приложение. Опциональная функция **per-user Kerberos** (`auth.per_user_enabled=true`) устраняет это: SSPI выполняется в отдельном helper-процессе **внутри сессии пользователя**, поэтому используется **личный Kerberos-билет (TGT)** пользователя, а токены брокерятся службе по защищённому IPC-каналу. Функция **опциональна** и по умолчанию выключена; при `per_user_enabled=false` relay работает ровно как раньше.

### 7.1. Обзор компонентов и поток

```
                         LocalSystem-процесс (TcpRedirectorService.exe)
  ┌───────────────────────────────────────────────────────────────────────────┐
  │  TcpRelayServer.ConnectionHandler                                          │
  │     │ соединение → PID (ConnectionTable / ProcessResolver)                 │
  │     │ PID → sessionId (ProcessIdToSessionId) → user SID                    │
  │     ▼                                                                       │
  │  SelectingAuthProviderFactory  (реализует таблицу политики §5 плана)       │
  │     │ выбирает провайдер на соединение:                                    │
  │     │   • LocalSspiProvider    — legacy (машинный аккаунт)                 │
  │     │   • BrokeredAuthProvider — per-user (через helper)                   │
  │     │   • DropAuthProvider     — fail-closed (drop/error)                  │
  │     ▼                                                                       │
  │  AuthHelperManager                                                         │
  │     - WTSEnumerateSessions → активные интерактивные сессии (не session 0)  │
  │     - запуск ОДНОГО helper'а на сессию (WTSQueryUserToken +                │
  │       CreateProcessAsUser), Job Object (kill-on-close), relaunch на крэше  │
  │     - обработка SESSIONCHANGE (logon/logoff/disconnect)                    │
  └───────────────────────────────┬───────────────────────────────────────────┘
                                   │ named-pipe (на сессию):
                                   │   \\.\pipe\TcpRedirectorAuth_<sessionId>
                                   │   служба = КЛИЕНТ, helper = СЕРВЕР
                                   ▼
                 Интерактивная сессия N (winsta0\Default, sessionId=N)
  ┌───────────────────────────────────────────────────────────────────────────┐
  │  TcpRedirectorAuthHelper.exe  (работает ОТ ИМЕНИ пользователя)             │
  │    - named-pipe СЕРВЕР, ACL: только владелец-пользователь + LocalSystem    │
  │    - на каждый запрос: SspiNegotiate(...) с Kerberos-билетом пользователя  │
  │    - держит SspiContext по correlation_id между шагами handshake           │
  │    - allow-list SPN = только SPN сконфигурированного прокси                │
  └───────────────────────────────────────────────────────────────────────────┘
```

### 7.2. Helper-процесс `TcpRedirectorAuthHelper.exe`

Исходники — в `src/service/AuthHelper/` (см. [`README.md`](../src/service/AuthHelper/README.md)). Крошечный headless x64-EXE без зависимостей от WinDivert/wintun. Он **не дублирует SSPI-логику**: проект компилирует тот же файл [`auth_sspi.cpp`](../src/service/TcpRedirectorService/infrastructure/auth/auth_sspi.cpp:1), что и служба. Ключевые части:

- [`AuthHelperMain.cpp`](../src/service/AuthHelper/AuthHelperMain.cpp) — точка входа: разбор CLI (`--session`, `--pipe`, `--nonce`, `--spn`/`--proxy-host`), отказ работать в session 0, watchdog по родителю, старт сервера.
- [`AuthPipeServer.h`](../src/service/AuthHelper/AuthPipeServer.h) — named-pipe-**сервер**: SDDL, проверка «клиент = LocalSystem», `hello`, цикл запросов, map `correlation_id → SspiContext` с TTL-GC, allow-list SPN, кэш credential-handle.

Так как процесс имеет **токен пользователя**, `AcquireCredentialsHandleW(NULL, L"Negotiate", …)` внутри helper'а получает билет **этого пользователя**.

### 7.3. Менеджер сессий `AuthHelperManager`

[`AuthHelperManager.h`](../src/service/TcpRedirectorService/infrastructure/auth/AuthHelperManager.h:1) — компонент службы, который:

1. перечисляет интерактивные сессии (`WTSEnumerateSessionsW`), пропуская session 0 и сессии без залогиненного пользователя;
2. запускает **ровно один** helper на подходящую сессию: `WTSQueryUserToken` → `DuplicateTokenEx` (primary) → `CreateEnvironmentBlock` → `CreateProcessAsUserW` (`lpDesktop = winsta0\default`);
3. отслеживает helper'ов (sessionId, user SID, PID, nonce, pipe name, SPN/host) в потокобезопасной таблице;
4. держит всех детей под **Job Object** с `KILL_ON_JOB_CLOSE` — helper'ы не переживают падение службы (нет сирот);
5. убирает helper'а на **logoff**/крэше и **сохраняет** его живым на RDP-**disconnect** (быстрый реконнект);
6. отдаёт `TryGet`/`BuildBrokeredParams`, чтобы relay нашёл «helper для сессии N»;
7. **(Задача 2)** экспонирует агрегированный **health-статус** подсистемы (есть ли живые helper'ы), который служба отдаёт GUI в поле `auth_status` ответа `service_status` (`disabled`/`active`/`no_helper`/`error`, см. §1.6). Это позволяет GUI показывать отдельный индикатор состояния Kerberos-авторизации, обновляющийся «на лету».

### 7.4. Резолв соединение → PID → сессия и абстракция провайдера

Relay-путь получает провайдер аутентификации на каждое соединение через **фабрику**. Абстракция построена вокруг порта [`IAuthProvider`](../src/service/TcpRedirectorService/domain/ports/IAuthProvider.h:1) («выдать следующий Negotiate-токен»), что позволяет прозрачно подменять реализацию:

| Реализация | Когда выбирается | Поведение |
|------------|------------------|-----------|
| `LocalSspiProvider` | `per_user_enabled=false`, либо fallback `system` | Legacy-SSPI под машинным аккаунтом (`SspiNegotiate` локально) |
| `BrokeredAuthProvider` | сессия резолвлена **и** helper найден | Токен запрашивается у helper'а сессии через `AuthBrokerClient` |
| `DropAuthProvider` | fallback `drop`/`error` | Возвращает `Failed` → relay закрывает соединение |

Всю политику выбора инкапсулирует [`SelectingAuthProviderFactory`](../src/service/TcpRedirectorService/infrastructure/auth/SelectingAuthProviderFactory.h:1). Для каждого соединения она:
1. если `per_user_enabled=false` → `LocalSspiProvider` (строго прежнее поведение);
2. иначе резолвит сессию (`IUserSessionResolver`: PID из `ConnectionTable` по `client_port`, иначе `ProcessResolver::ResolvePidBySourcePort`, затем `ProcessIdToSessionId`);
3. если сессия резолвлена и `AuthHelperManager` вернул параметры helper'а → `BrokeredAuthProvider`;
4. иначе применяет `fallback_policy`: `system` → `LocalSspiProvider`, `drop`/`error` → `DropAuthProvider`.

### 7.5. IPC-брокеринг токенов

Транспорт — named-pipe, **по одному на сессию**: `\\.\pipe\TcpRedirectorAuth_<sessionId>` (session id в имени исключает коллизии между RDP-пользователями). Роли **обратны** GUI-каналу: **helper — сервер**, **служба — клиент**. Схема сообщений — единый источник истины [`AuthBrokerProtocol.h`](../src/shared/auth_broker/AuthBrokerProtocol.h:1) (JSON, `PIPE_TYPE_MESSAGE`):

- `hello` (helper → служба при подключении) — несёт `session_id` и одноразовый `nonce`, выданный менеджером при запуске (защита от squatting'а имени pipe);
- `sspi_step` (служба → helper) — один шаг Negotiate; `server_token` пуст на первом шаге; `correlation_id` уникален на соединение relay и переиспользуется между шагами, чтобы helper переиспользовал `SspiContext`;
- ответ на `sspi_step` — статус (`continue`/`complete`/`no_credentials`/`denied`/`error`) + `out_token`;
- `release` (служба → helper) — освободить `SspiContext` по завершении/ошибке соединения (helper также GC'ит контексты по TTL).

Многошаговый handshake `407` коррелируется по `correlation_id`; таймаут одного вызова — `auth.helper_timeout_ms`.

### 7.6. Обработка SESSIONCHANGE

Чтобы менеджер знал о logon/logoff/disconnect, служба ([`main.cpp`](../src/service/TcpRedirectorService/main.cpp:1) / [`ServiceMain.h`](../src/service/TcpRedirectorService/adapters/driving/ServiceMain.h:1)) регистрирует обработчик с `SERVICE_ACCEPT_SESSIONCHANGE` и в `ServiceControlHandlerEx` обрабатывает `SERVICE_CONTROL_SESSIONCHANGE` (`WTS_SESSION_LOGON`, `WTS_SESSION_LOGOFF`, `WTS_SESSION_UNLOCK`, `WTS_SESSION_REMOTE_CONNECT`/`DISCONNECT`), форвардя события в `AuthHelperManager`. Logon → запуск helper'а; logoff → его убийство; disconnect → helper остаётся жив.

### 7.7. Модель безопасности

- **ACL pipe.** Helper создаёт pipe с SDDL `O:SYG:SYD:(A;;GA;;;SY)(A;;GA;;;<owner-user-SID>)` — доступ **только** владельцу-пользователю (SID из `TokenUser`) и LocalSystem (`SY`). `BUILTIN\Administrators` намеренно **не** добавлен, поэтому админ из другой сессии не откроет чужой helper-pipe. `FILE_FLAG_FIRST_PIPE_INSTANCE` защищает от squatting'а имени.
- **Взаимная проверка канала.** Служба сверяет `hello`-nonce (и, опционально, PID сервера через `GetNamedPipeServerProcessId`). Helper через `ImpersonateNamedPipeClient` требует, чтобы клиент был **LocalSystem** (`S-1-5-18`); любой другой — отклоняется.
- **Ограничение token-oracle.** Helper выпускает токены **только** для SPN из allow-list (SPN прокси из `auth.spn` / хоста прокси); прочие SPN → `denied` (никогда не откатывается молча). По каналу передаются **только** непрозрачные Negotiate-блобы — никогда пароли или TGT.
- **Ортогональность GUI-IPC.** Канал GUI↔служба ([`TcpIpcServer.h`](../src/service/TcpRedirectorService/infrastructure/ipc/TcpIpcServer.h:1), `.ipc_token`) не связан с auth-брокером: другое имя, направление и назначение.

Полное описание конфигурации per-user-полей — в [`docs/КОНФИГУРАЦИЯ.md`](КОНФИГУРАЦИЯ.md) §7; ограничения — в [`docs/ИЗВЕСТНЫЕ_ПРОБЛЕМЫ.md`](ИЗВЕСТНЫЕ_ПРОБЛЕМЫ.md); план проверки — [`tests/PER_USER_AUTH_TEST_PLAN.md`](../tests/PER_USER_AUTH_TEST_PLAN.md).
