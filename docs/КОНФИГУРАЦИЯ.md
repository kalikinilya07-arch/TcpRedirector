# Конфигурация: `config.json` (схема v2)

Документ полностью описывает файл конфигурации TcpRedirector версии схемы **v2**. Структуры данных определены в [`Config.h`](../src/service/TcpRedirectorService/infrastructure/config/Config.h:1), логика чтения/записи и валидации — в [`ConfigManager.cpp`](../src/service/TcpRedirectorService/infrastructure/config/ConfigManager.cpp:1).

> Все ключи JSON пишутся **как показано**. Обратите внимание: v2-секции используют `snake_case` (`capture_mode`, `route_all_traffic`, `port_ranges`, `tunnel_ipv4_cidr`), тогда как исторические v1-секции (`proxy`, `auth`, `log`, `stats`) используют `camelCase` для внутренних полей (`fileEnabled`, `maxSizeMB`, `encryptedPassword`, `updateIntervalMs`, `exePath`). Это фактическое поведение кода.

---

## 1. Расположение файла и миграция

- Файл `config.json` находится **рядом с исполняемым файлом службы** (`<exeDir>\config.json`), путь резолвится через [`AppPaths.h`](../src/service/TcpRedirectorService/infrastructure/paths/AppPaths.h:82). GUI читает/пишет **тот же** файл (GUI устанавливается в подкаталог `gui\`, а конфиг лежит на уровень выше).
- При установке `config.json` создаётся из seed-файла `config.default.json` (см. [`installer/config.default.json`](../installer/config.default.json)) — только если он ещё не существует.
- **Миграция:** при первом старте, если `<exeDir>\config.json` отсутствует, но существует `%ProgramData%\TcpRedirector\config.json`, служба один раз копирует его рядом с EXE (см. `EnsureConfigMigrated()` в [`ConfigManager.cpp`](../src/service/TcpRedirectorService/infrastructure/config/ConfigManager.cpp:47)).
- Если файла нет и мигрировать нечего — служба создаёт дефолтный конфиг сама.

## 2. Общая структура

```json
{
  "config_version": 2,
  "capture_mode": "wintun",
  "app": { ... },
  "proxy": { ... },
  "auth": { ... },
  "log": { ... },
  "stats": { ... },
  "ipc": { ... },
  "gui": { ... },
  "wintun": { ... },
  "apps": [ ... ],
  "rules": [ ... ]
}
```

| Ключ | Тип | Назначение |
|------|-----|------------|
| `config_version` | int | Маркер схемы; для v2 равен `2`. Отсутствие поля означает v1 |
| `capture_mode` | string | Активный движок захвата: `"windivert"` или `"wintun"` |
| `app` | object | Legacy-секция целевого процесса (совместимость с v1) |
| `proxy` | object | Параметры вышестоящего HTTP-прокси |
| `auth` | object | Авторизация на прокси |
| `log` | object | Логирование |
| `stats` | object | Статистика для GUI |
| `wintun` | object | Настройки Wintun-адаптера и tun2socks-движка |
| `apps` | array | Пер-приложение правила (v2) |
| `rules` | array | Legacy-зеркало правил (генерируется автоматически) |
| `ipc` | object | Настройки IPC-канала управления (см. §9а) |
| `gui` | object | GUI-специфичные настройки, напр. язык интерфейса (см. §9б); служба игнорирует |

---

## 3. `config_version`

- **Тип:** int. **По умолчанию:** `2`.
- Конфиги без этого поля (или со значением < 2) считаются **v1** и «на лету» преобразуются в v2: legacy `rules[]` синтезируются в `apps[]`.

---

## 4. `capture_mode`

- **Тип:** string. **По умолчанию:** `"wintun"` (движок `embedded`).
- **Допустимые значения:** `"windivert"`, `"wintun"` (регистр-независимо).
- Отсутствующее/пустое значение трактуется как `"wintun"`.
- Неизвестное значение приводится к `"wintun"` с предупреждением в лог.
- **Дефолт после установки** — `"wintun"` + `wintun.engine="embedded"` (см. seed-конфиг [`installer/config.default.json`](../installer/config.default.json)). Ранее дефолтом был `"windivert"`.
- Определяет, какой механизм захвата активируется и какой preflight выполняется. См. [`docs/ПЕРЕКЛЮЧЕНИЕ_РЕЖИМА.md`](ПЕРЕКЛЮЧЕНИЕ_РЕЖИМА.md).

## 7. `auth`

```json
"auth": {
  "enabled": false,
  "kerberos": false,
  "username": "",
  "encryptedPassword": "",
  "encryptPassword": true,
  "password": "",
  "per_user_enabled": false,
  "spn": "",
  "fallback_policy": "drop",
  "helper_timeout_ms": 5000
}
```

| Поле | Тип | По умолчанию | Описание |
|------|-----|--------------|----------|
| `enabled` | bool | `false` | Требуется ли авторизация на прокси |
| `kerberos` | bool | `false` | `true` — использовать Negotiate/**Kerberos** (SSPI, доменная авторизация без пароля); `false` — **Basic** |
| `username` | string | `""` | Логин для Basic Auth |
| `encryptedPassword` | string | `""` | Пароль для Basic Auth, зашифрованный через **DPAPI** и закодированный Base64. Используется при `encryptPassword=true` |
| `encryptPassword` | bool | `true` | **(Задача №2)** Шифровать ли пароль. `true` — прежнее поведение (DPAPI → `encryptedPassword`). `false` — пароль хранится/используется **как есть** (plaintext) в поле `password`, в обход DPAPI |
| `password` | string | `""` | Пароль **в открытом виде**. Используется **только** при `encryptPassword=false`. ⚠️ Хранится в `config.json` незашифрованным — только для доверенного окружения/диагностики |
| `per_user_enabled` | bool | `false` | **(Per-user Kerberos, Variant 4b)** Включить per-user Kerberos auth helper: SSPI выполняется в per-user helper-процессе (`TcpRedirectorAuthHelper.exe`) **от имени вошедшего пользователя**, поэтому на прокси предъявляется билет пользователя, а не машинного аккаунта LocalSystem. Требует `kerberos=true`. По умолчанию **выключено** (полностью прежнее поведение) |
| `spn` | string | `""` | **(Per-user Kerberos)** Явное переопределение SPN, для которого helper выпускает Negotiate-токен (это же значение — allow-list helper'а). Пусто = авто-деривация `HTTP/<proxy_host>` в рантайме (см. `MakeSpn` в [`auth_sspi.cpp`](../src/service/TcpRedirectorService/infrastructure/auth/auth_sspi.cpp)) |
| `fallback_policy` | string | `"drop"` | **(Per-user Kerberos)** Политика отката, когда per-user-аутентификация невозможна (helper недоступен, PID→user не резолвится, таймаут IPC, режим external tun2socks). Значения: `"drop"` (закрыть соединение — **никогда** не откатываться на машинный аккаунт молча; **дефолт по решению безопасности, fail-closed**), `"system"` (легаси-аутентификация машинным аккаунтом LocalSystem — прежнее «мягкое» поведение), `"error"` (закрыть + `proxy_errors`++ + запись WARN в лог). Неизвестное значение приводится к `"drop"` |
| `helper_timeout_ms` | int | `5000` | **(Per-user Kerberos)** Таймаут одного запроса к helper по IPC (мс). По истечении helper считается недоступным → применяется `fallback_policy` |

> **Per-user Kerberos auth helper (Variant 4b).** Поля `per_user_enabled`, `spn`,
> `fallback_policy`, `helper_timeout_ms` управляют опциональной
> **per-user-аутентификацией на прокси**. Когда `per_user_enabled=true`, служба
> запускает в каждой активной интерактивной сессии helper-процесс
> `TcpRedirectorAuthHelper.exe`, который выполняет SSPI/Negotiate **в контексте
> вошедшего пользователя** и по защищённому named-pipe отдаёт relay Negotiate-токен
> с идентичностью пользователя (а не машинного аккаунта). Архитектуру см. в
> [`docs/АРХИТЕКТУРА.md`](АРХИТЕКТУРА.md) §7; план проверки на доменном стенде —
> [`tests/PER_USER_AUTH_TEST_PLAN.md`](../tests/PER_USER_AUTH_TEST_PLAN.md).
>
> **Обратная совместимость.** Все четыре поля **опциональны**: конфиги без них
> загружаются с безопасными дефолтами (`per_user_enabled=false`,
> `fallback_policy="drop"`, `helper_timeout_ms=5000`, `spn=""`). При
> `per_user_enabled=false` поведение auth/relay **байт-в-байт совпадает** с прежним
> (машинная SSPI-аутентификация под LocalSystem, `LocalSspiProvider`); helper не
> запускается. Обратите внимание: в отличие от исторических camelCase-полей секции
> `auth`, новые поля используют `snake_case`.
>
> **Дефолт `fallback_policy="drop"` (fail-closed).** Когда per-user-аутентификация
> невозможна, соединение **закрывается** — служба **никогда** не откатывается на
> машинный аккаунт молча. Чтобы вернуть прежнее «мягкое» поведение (при сбое
> использовать машинную аутентификацию), задайте `fallback_policy="system"`.
>
> **Требования и ограничения.** Нужен домен AD и пользователь с реальным
> Kerberos-билетом (интерактивный/консольный/RDP-вход); действуют те же условия
> настоящего Kerberos, что перечислены ниже (FQDN прокси и т.д.). В режиме
> **Wintun + external (`tun2socks`)** per-user-аутентификация **недоступна** (нельзя
> сопоставить соединение с исходным PID/пользователем) — применяется
> `fallback_policy`. Подробнее об ограничениях — в
> [`docs/ИЗВЕСТНЫЕ_ПРОБЛЕМЫ.md`](ИЗВЕСТНЫЕ_ПРОБЛЕМЫ.md).

> **Когда отключать шифрование (`encryptPassword=false`).** DPAPI-блоб привязан к учётной записи/машине; при переносе конфига, смене аккаунта службы или рассинхроне scope пароль может перестать расшифровываться, и Basic-auth молча перестаёт работать (`DecryptPassword` возвращает пусто). Режим plaintext снимает этот класс проблем: пароль можно вписать руками в `auth.password`, а служба использует его без DPAPI. Задаётся и из GUI (снимите флажок «Шифровать пароль (DPAPI)»).

> При включённом Kerberos служба принудительно считает `auth_required=true` (см. [`ServiceMain.h`](../src/service/TcpRedirectorService/adapters/driving/ServiceMain.h:103)). Пароль при Kerberos не нужен — используется контекст текущей учётной записи через SSPI.

> **Требования для настоящего Kerberos (важно).** SSPI-пакет `Negotiate` сам
> выбирает между Kerberos и NTLM. Реальный Kerberos-билет получается **только**
> при одновременном соблюдении условий:
> 1. **Домен.** Машина в домене AD. В рабочей группе (workgroup) Kerberos
>    невозможен — Negotiate молча **откатывается на NTLM**.
> 2. **FQDN прокси.** `proxy.host` должен быть задан **доменным именем** (FQDN),
>    т.к. SPN формируется как `HTTP/<host>` ([`auth_sspi.cpp`](../src/service/TcpRedirectorService/infrastructure/auth/auth_sspi.cpp)). Для **IP-литерала**
>    (напр. `127.0.0.1` у заглушки) Kerberos-SPN не существует — служба логирует
>    предупреждение и SSPI уходит в NTLM.
> 3. **Учётная запись.** Служба по умолчанию работает под `LocalSystem` (identity =
>    машинный аккаунт домена). Для доменного Kerberos от имени пользователя
>    запускайте под доменной учётной записью, у которой есть билет.
>
> **Диагностика в логе.** При `log.level=DEBUG` relay пишет получение токена и
> (для IP-хоста) предупреждение о фолбэке на NTLM. Тестовая **заглушка** в режиме
> `--auth-mode challenge` логирует подтип токена (`token_subtype=NTLM Type1/2/3`
> или `Kerberos/SPNEGO`) — так видно, что реально используется. См. `stub/README.md`.
>
> **CONNECT-ответ прокси.** Relay дочитывает ответ на `CONNECT` до конца
> заголовков (`\r\n\r\n`) и, если прокси прислал первые байты туннеля вместе с
> `200`, форвардит их клиенту перед стартом моста — раньше такой «хвост» терялся.

> **Очистка неактуальных полей auth при пересохранении (Задача №2).** При каждом
> сохранении конфигурации (из GUI или службой) поля секции `auth`, не относящиеся
> к текущему режиму, **очищаются**, чтобы в `config.json` не оставались «мусорные»
> значения от деактивированных настроек:
> - `enabled=false` → очищаются `username`, `encryptedPassword`, `password`;
> - `kerberos=true` → очищаются `username`, `encryptedPassword`, `password`
>   (Kerberos не хранит креды);
> - Basic + `encryptPassword=true` → очищается `password` (plaintext);
> - Basic + `encryptPassword=false` → очищается `encryptedPassword` (DPAPI).
>
> Правило применяется даже если пользователь не вводил новый пароль (например,
> просто переключил `encryptPassword` или переключился Basic↔Kerberos и обратно).
> GUI-сторона реализует это в [`JsonConfigRepository.WriteFullV2`](../src/gui/TcpRedirectorGUI/Infrastructure/Config/JsonConfigRepository.cs), служба — в
> `ConfigManager::NormalizeAuthFields()` (вызывается из `SaveImpl()`).

> **Скрытие полей при Kerberos (Задача №3).** В GUI при включённом флажке
> «Use Kerberos protocol» поля ввода **Login** и **Password**, а также чекбокс
> «Шифровать пароль (DPAPI)» **скрываются** (для Kerberos они не нужны). При
> снятии флажка Kerberos поля снова отображаются. Сам чекбокс Kerberos остаётся
> видимым, пока авторизация включена.

> **Как задаётся пароль (важно).** GUI **не** пишет `encryptedPassword` в `config.json` напрямую — он не может зашифровать секрет под учётной записью службы (DPAPI привязан к аккаунту). Вместо этого GUI передаёт пароль в открытом виде службе по **аутентифицированному** IPC-каналу (см. раздел про IPC в [`АРХИТЕКТУРА.md`](АРХИТЕКТУРА.md)), а служба шифрует его через DPAPI и сохраняет в `config.json`. Поэтому значение читаемо/расшифровываемо только на той же машине под тем же аккаунтом, под которым работает служба; при переносе на другой ПК/аккаунт пароль нужно ввести заново.

## 8. `log`

```json
"log": { "level": 2, "fileEnabled": true, "maxSizeMB": 50 }
```

| Поле | Тип | По умолчанию | Описание |
|------|-----|--------------|----------|
| `level` | int | `2` | Уровень **в файловой шкале службы**: `0`=ERROR, `1`=WARN, `2`=INFO, `3`=DEBUG, `4`=TRACE |
| `fileEnabled` | bool | `true` | Писать ли лог в файл |
| `maxSizeMB` | int | `50` | Максимальный размер файла лога (МБ) до ротации (совпадает с `LogSettings::maxSizeMB`) |

Логи пишутся в `<exeDir>\logs\`.

> **Шкала `log.level` (важно).** В `config.json` уровень хранится в **файловой
> шкале службы** (`0`=ERROR, `1`=WARN, `2`=INFO, `3`=DEBUG, `4`=TRACE) — именно её
> читает `ConfigManager::GetLogLevel`. GUI показывает **доменную** 5-уровневую
> шкалу (`0`=TRACE, `1`=DEBUG, `2`=INFO, `3`=WARN, `4`=ERROR — как в
> `domain::LogLevel` и в живом IPC `set_log_level`) и **транслирует** её в
> файловую шкалу при записи/чтении `config.json`. Живой IPC-вызов уровня идёт
> в доменной шкале. (Ранее GUI писал доменное число прямо в файл, из-за чего
> уровень инвертировался — исправлено, см. `ИЗВЕСТНЫЕ_ПРОБЛЕМЫ.md`, B3.)

> **ВАЖНО (исправление 15.07.2026).** Ранее уровень из `config.json` **не
> применялся при старте службы**: `ServiceMain` инициализировал логгер жёстко
> на `INFO` и после загрузки конфига вызывал только установку размера файла, но
> **не** `SetLevel`. Из-за этого смена `log.level` в конфиге ни на что не влияла
> (в частности, DEBUG-логи не появлялись). Теперь уровень применяется при старте
> из `config.json`. Дополнительно добавлен экспертный уровень **`4`=TRACE**: он
> включает максимально подробную диагностику, в т.ч. Wintun-строки
> `[wintun][rx-stats]`, `[wintun][PROXY]`, `[wintun][DIRECT-drop]`. Ключевые из
> них (`rx-stats`, `DIRECT-drop`) понижены до **DEBUG** и видны уже на `level=3`.
> Для полной трассировки установите `level=4` (в GUI — пункт «TRACE+», либо
> ручной правкой конфига).
>
> **Диагностика Wintun «трафик не выходит на прокси».** Включите `level=3`
> (лучше `4`), режим `capture_mode=wintun`, `engine=embedded`,
> `wintun.process_filter_enabled=false`, затем по логу локализуйте стадию:
> - нет `[wintun][rx-stats] … ipv4>0` и `Get-NetAdapterStatistics TcpRedirector`
>   `ReceivedBytes=0` → трафик **не доходит до TUN** (маршрутизация: сторонний
>   VPN/WireGuard или «протёкший» proxy-bypass; выключите сторонний VPN);
> - `ipv4>0`, но нет `[wintun][flow] PROXY …` → трафик входит, но не проксируется;
> - есть `PROXY … connect=OK`, но нет relay `CONNECT … 200 OK` → проблема на
>   стыке relay↔прокси (доступность/адрес/порт/авторизация);
> - `[wintun][flow] connect to relay … FAILED (WSA=…)` → relay не слушает.

## 9а. `ipc`

Настройки локального канала управления (GUI ↔ служба, TCP `127.0.0.1:34011`).

```json
"ipc": { "auth_enabled": true }
```

| Поле | Тип | По умолчанию | Описание |
|------|-----|--------------|----------|
| `auth_enabled` | bool | `true` | **(Задача №1)** Требовать ли токен-аутентификацию на IPC-канале. `true` — прежнее поведение: служба генерирует `.ipc_token` (DACL Administrators/SYSTEM) и отклоняет запросы без корректного токена. `false` — аутентификация **не** навязывается: любой локальный клиент управляет службой без токена/привилегий |

> ⚠️ **Безопасность.** `auth_enabled=false` повышает локальную поверхность атаки —
> любой процесс на той же машине сможет управлять службой через loopback-порт.
> Используйте только для диагностики/в доверенном окружении. Изменение вступает
> в силу **после перезапуска службы**. Задаётся и из GUI (раздел «Дополнительно
> (IPC / безопасность)»). Отключение IPC-аутентификации **не влияет** на
> перехват/форвардинг трафика — это лишь канал управления.


|------|-----|--------------|----------|
| `adapter_name` | string | `"TcpRedirector"` | Отображаемое имя Wintun-адаптера. Не должно быть пустым (иначе preflight fail) |
| `adapter_guid` | string | `""` | GUID адаптера. Пусто — генерируется при первом старте и сохраняется |
| `tunnel_ipv4_cidr` | string | `"10.6.7.1/24"` | IPv4-CIDR TUN-стороны (`a.b.c.d/N`, `N` ∈ [0..32]). Невалидное значение → откат к дефолту с предупреждением |
| `tunnel_ipv6_cidr` | string | `""` | IPv6-CIDR. **Пусто = IPv6-туннель выключен.** В v1 IPv6 в Wintun-режиме по умолчанию отключён |
| `mtu` | int | `1500` | MTU интерфейса. Значение зажимается в диапазон [576; 65535] |
| `engine` | string | `"embedded"` | Тип движка: `"embedded"` (встроенный lwIP) или `"external"` (внешний `tun2socks.exe`). Неизвестное → `"embedded"` с предупреждением |
| `process_filter_enabled` | bool | `true` | **Фильтрация по процессу внутри Wintun-движка.** При `true` embedded-движок применяет те же `apps[]`-правила, что и WinDivert (PROXY/DIRECT/BLOCK). При `false` — весь IPv4-TCP гонится через прокси без разбора процесса. Подробнее — §10.2. **На `engine="external"` не влияет** (см. ограничение в §10.2) |
| `block_ipv6` | bool | `true` | **Нейтрализация IPv6 на время Wintun-захвата.** Туннель/relay/HTTP `CONNECT` — только IPv4, а на dual-stack хостах ОС (RFC 6724) предпочитает глобальный IPv6, и трафик уходит мимо TUN (симптом: «работает через IPv6», проксирование не происходит). При `true` служба заворачивает весь IPv6 в TUN (маршруты `::/1` + `8000::/1`), а embedded-движок отвечает **TCP RST** на IPv6-SYN → приложение мгновенно откатывается на IPv4 (который идёт в туннель и проксируется); не-TCP IPv6 дропается. Всё снимается на Close. При `false` IPv6 не трогается (возможна утечка мимо прокси). Подробнее — §10.3 |
| `external_engine` | object | — | Настройки внешнего движка (используются только при `engine="external"`) |

| `extra_args` | array of string | `[]` | Дополнительные аргументы CLI, передаются процессу как есть |
| `socks5_listen` | string | `"127.0.0.1:1080"` | Адрес `host:port` локального SOCKS5-слушателя relay, куда форвардит `tun2socks`. Невалидное → откат к `127.0.0.1:1080` |
| `restart_on_crash` | bool | `true` | Автоперезапуск дочернего процесса при падении |

### 10.2. Фильтрация по процессу в Wintun-режиме

Начиная с этой версии фильтрация по конкретному процессу работает **не только в WinDivert, но и в Wintun-режиме** — поведение стало консистентным между режимами. Управляется полем `wintun.process_filter_enabled` (по умолчанию `true`).

**Embedded-движок (`engine="embedded"`).** В момент приёма каждого TCP-соединения из туннеля движок:

1. Резолвит процесс-источник по локальному (source) порту через `GetExtendedTcpTable(TCP_TABLE_OWNER_PID_ALL)` (с PID-кэшем TTL 30 c и одним ретраем через 20 мс при промахе — TCP-таблица ОС может отставать).
2. Получает полный путь процесса (`OpenProcess` + `QueryFullProcessImageNameW`).
3. Спрашивает те же правила `apps[]` (`RuleEngine::MatchForFlow`, затем legacy-`Match`, затем fallback по `app.exePath` + дерево процессов для helper/child-процессов), что и WinDivert.
4. Применяет решение:
   - **PROXY** (правило сработало) → перед форвардом на relay движок регистрирует `(эфемерный порт loopback-сокета → original-dst)` в `ConnectionTable`, чтобы relay восстановил адрес назначения; затем соединение форвардится на прокси;
   - **DIRECT** (правило не сработало) → соединение **отклоняется** (`tcp_abort`, fail-fast). **Важно:** в embedded «прямой проход» не-целевого трафика мимо прокси **не поддерживается** — исходящий сокет по split-tunnel-маршрутам ушёл бы обратно в тот же TUN на том же engine-треде и заморозил бы стек. Поэтому не-целевой трафик в embedded с `process_filter_enabled=true` отбрасывается;
   - **BLOCK** (legacy-правило с действием block) → соединение отклоняется (`tcp_abort`).

> **Как выбрать режим для своей задачи.**
> - Нужно **проксировать весь** трафик → `process_filter_enabled=false` (весь IPv4-TCP через прокси, DIRECT не возникает).
> - Нужно проксировать **только выбранные** приложения, а остальное оставить работать напрямую → используйте `capture_mode=windivert` (в WinDivert DIRECT работает штатно: пакеты не переехаливаются в TUN). В embedded не-целевой трафик будет отброшен.

Если `process_filter_enabled=false`, embedded-движок работает по Option 2b: весь IPv4-TCP гонится через прокси без разбора процесса (DIRECT не возникает).

> **Смысл `apps[]` в Wintun.** Теперь `pattern`, `ports`, `port_ranges`, `route_all_traffic` (см. §11) реально влияют на embedded-Wintun так же, как на WinDivert. Приложение проксируется, только если сматчилось правило; иначе — прямой выход.

### 10.3. Нейтрализация IPv6 в Wintun-режиме (`block_ipv6`)

Весь путь Wintun-режима — туннель, split-tunnel-маршруты, embedded lwIP, relay и HTTP `CONNECT` — работает **только по IPv4**. Если на хосте активен глобальный IPv6 (типично для домашних/офисных сетей), то по правилам выбора адреса назначения (RFC 6724) Windows **предпочитает** глобальный IPv6 IPv4 для dual-stack адресатов. В результате `ping`, браузеры и утилиты уходят по физическому IPv6 **мимо** IPv4-TUN, и проксирование не срабатывает («трафик работает через IPv6»).

При `block_ipv6=true` (по умолчанию) служба на старте Wintun-захвата:

1. Ставит на Wintun-адаптер маршруты `::/1` и `8000::/1` (on-link, `NETMGMT`, метрика 1) — весь IPv6 заворачивается в TUN.
2. Embedded-движок, получая IPv6-пакет из туннеля, **не** передаёт его в lwIP (IPv4-only): на IPv6 TCP-**SYN** он формирует и отправляет обратно в туннель **IPv6 TCP RST**, из-за чего приложение немедленно отказывается от IPv6 и повторяет соединение по IPv4 (который идёт в туннель и проксируется). Прочий IPv6 (не-SYN TCP, UDP, ICMPv6) дропается.
3. При `Close` маршруты `::/1` + `8000::/1` снимаются.

Ограничение v1: полноценное проксирование IPv6 (IPv6→прокси) не поддерживается — используется быстрый откат на IPv4. Если вышестоящий прокси задан IPv6-литералом/AAAA — этот кейс пока не покрыт (нужен `/128`-bypass); используйте IPv4-адрес прокси. Отключить поведение целиком можно `block_ipv6=false` (тогда IPv6 может утечь мимо прокси).

**Ограничение external-движка (`engine="external"`).** Фильтрация по конкретному процессу на уровне отдельного соединения в external-режиме **невозможна** тем же способом. Трафик терминирует дочерний `tun2socks.exe` и форвардит его на loopback-SOCKS5. На границе SOCKS5 источником любого соединения является **сам `tun2socks.exe`** (его PID), а не оригинальное приложение; `tun2socks` к тому же не сохраняет source-порт исходного приложения. Поэтому в external-режиме `process_filter_enabled` **игнорируется**: весь трафик туннеля проксируется (при `true` в лог пишется предупреждение). Для фильтрации по процессу используйте `engine="embedded"` либо `capture_mode="windivert"`.

## 11. `apps` (правила v2)

Массив пер-приложение правил. Каждый элемент:

```json
{
  "exe_path": "C:\\Apps\\MyApp\\MyApp.exe",
  "pattern": "MyApp.exe",
  "proxy_id": "default",
  "route_all_traffic": false,
  "ports": [443, 8443],
  "port_ranges": [ { "from": 5000, "to": 5010 } ]
}
```

| Поле | Тип | По умолчанию | Описание |
|------|-----|--------------|----------|
| `exe_path` | string | `""` | Опциональный полный путь к EXE (для UX/логов) |
| `pattern` | string | — (обязателен) | Шаблон имени/пути процесса. **Пустой `pattern` → правило пропускается** с предупреждением |
| `proxy_id` | string | `""` | Идентификатор прокси (сейчас используется `"default"`) |
| `route_all_traffic` | bool | `false` | `true` — весь TCP-трафик приложения идёт через прокси, поля портов **игнорируются** |
| `ports` | array of int | `[]` | Дискретные порты назначения (1..65535). Дубликаты и невалидные значения отбрасываются |
| `port_ranges` | array of object | `[]` | Диапазоны портов `{ "from": N, "to": M }`, где `1 ≤ from ≤ to ≤ 65535` |

### Логика сопоставления

Процесс подходит по `pattern`. Затем проверяется порт назначения:

```
port_match = route_all_traffic
           OR (dst_port ∈ ports)
           OR (∃ range ∈ port_ranges: range.from ≤ dst_port ≤ range.to)
```

Правило срабатывает при совпадении процесса **и** порта. Если `route_all_traffic=false`, а `ports` и `port_ranges` пусты — правило **ничего не отматчит** (об этом пишется предупреждение при загрузке). В GUI поля портов деактивируются, когда включён флаг «весь трафик».

## 12. `rules` (legacy-зеркало)

- **Тип:** array. Генерируется автоматически при сохранении из `apps[]` (для совместимости со старыми v1-читателями).
- Правила с `route_all_traffic=true` в зеркало **не** попадают (v1 не умеет выражать «любой порт»). Диапазоны разворачиваются в плоский список с ограничением 128 записей.
- Вручную это поле редактировать не нужно.

```cmd
sc stop TcpRedirectorService
sc start TcpRedirectorService
```

Смена `capture_mode`/`engine` требует перезапуска — подробнее в [`docs/ПЕРЕКЛЮЧЕНИЕ_РЕЖИМА.md`](ПЕРЕКЛЮЧЕНИЕ_РЕЖИМА.md).
