# Риски, ограничения и производительность

## 1. Технические риски

### Риск 1: WinDivert driver не найден / остановлен

**Описание**: WinDivert64.sys должен быть зарегистрирован как Windows-сервис и запущен.

**Митигация**: `EnsureDriverRunning()` в `WinDivertCapture::Open()` — автоматически запускает драйвер при старте сервиса. Если драйвер не зарегистрирован — создаёт службу, указывая на `WinDivert64.sys` рядом с exe.

**Вероятность**: Низкая (после добавления EnsureDriverRunning)

### Риск 2: PID lookup не находит порт

**Описание**: `GetExtendedTcpTable` может не содержать запись для свежего SYN-пакета.

**Митигация**: H6 fix — PID-кэш с TTL 30 секунд. После первого успешного lookup порт кэшируется.

### Риск 3: Антивирусы блокируют WinDivert

**Описание**: WinDivert использует NDIS-драйвер для перехвата пакетов, что может детектироваться как подозрительное поведение.

**Митигация**: Добавление в исключения антивируса. Graceful degradation: при ошибке WinDivert сервис логирует ошибку и завершается (без захвата пакетов функциональность невозможна).

### Риск 4: Производительность при высокой нагрузке

**Описание**: CaptureLoop обрабатывает каждый пакет. При 50k pps — 20 мкс на пакет.

**Митигация**:
- PID lookup только для новых соединений (SYN)
- Per-port bitmap для кэширования решений (O(1))
- PID-кэш с TTL 30с
- Pre-allocated buffers в CaptureLoop
- Lock-free счётчики (std::atomic)

## 2. Ограничения

### Функциональные

| Ограничение | Причина |
|-------------|---------|
| Только HTTP CONNECT | Архитектурное решение |
| Только TCP | Фильтр WinDivert: `tcp and (outbound or ...)` |
| Нет QUIC/HTTP3 | QUIC использует UDP |
| Один upstream прокси | Конфигурация |
| Только IPv4 | Текущая реализация |

### Системные

| Ограничение | Значение |
|-------------|----------|
| Макс. одновременных соединений | 65535 (лимит портов) |
| Relay-потоков на соединение | 1 |
| Размер стека relay-потока | ~1 MB |
| Макс. правил RuleEngine | Не ограничено |
| Требуемые права | Администратор (для WinDivert) |

### Совместимость с прокси

- Обязательно: HTTP CONNECT метод (RFC 7231)
- Обязательно: HTTP/1.1 200 Connection Established
- Опционально: Basic Authentication (RFC 7617)
- Опционально: Negotiate/Kerberos (RFC 4559)

## 3. Производительность

### Оценка памяти

| Компонент | Расход |
|-----------|--------|
| На одно relay-соединение (с потоком) | ~1.1 MB |
| Service overhead | ~30 MB |
| WinDivert очередь (32 MB) | ~32 MB |
| GUI | ~70 MB |
| **Итого (без соединений)** | **~130 MB** |
| **На 100 соединений** | **~240 MB** |
| **На 1000 соединений** | **~1.2 GB** |

Основной расход — стеки потоков (1 MB на соединение). Возможна оптимизация уменьшением размера стека до 256 KB.

### Узкие места

1. **Thread-per-connection в TcpRelayServer**: 1000 потоков при 1000 соединений
2. **PID lookup через TCP table**: только для новых соединений (кэшируется)
3. **WinDivert очередь**: может расти при высокой нагрузке
