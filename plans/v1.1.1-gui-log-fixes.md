# План исправлений v1.1.1 — Баги GUI и логирования

## Диагностика

### Баг 1: Уровень логирования не меняется

**Корневая причина:** Инвертированный mapping между `domain::LogLevel` и `m_config.log.level` в [`ConfigManager::SetLogLevel`](TcpRedirector/src/service/TcpRedirectorService/infrastructure/config/ConfigManager.cpp:114) и [`GetLogLevel`](TcpRedirector/src/service/TcpRedirectorService/infrastructure/config/ConfigManager.cpp:103).

```cpp
// LogLevel enum: Trace=0, Debug=1, Info=2, Warn=3, Error=4

// ТЕКУЩИЙ (сломанный) mapping в SetLogLevel:
case domain::LogLevel::Error: m_config.log.level = 0; break;  // Error(4)→0 — НЕВЕРНО
case domain::LogLevel::Warn:  m_config.log.level = 1; break;  // Warn(3)→1  — НЕВЕРНО
case domain::LogLevel::Info:  m_config.log.level = 2; break;  // Info(2)→2  — верно
case domain::LogLevel::Debug: m_config.log.level = 3; break;  // Debug(1)→3 — НЕВЕРНО
// Trace(0) → default → 2 (Info) — НЕВЕРНО

// ПРАВИЛЬНЫЙ mapping:
case domain::LogLevel::Trace: m_config.log.level = 0; break;
case domain::LogLevel::Debug: m_config.log.level = 1; break;
case domain::LogLevel::Info:  m_config.log.level = 2; break;
case domain::LogLevel::Warn:  m_config.log.level = 3; break;
case domain::LogLevel::Error: m_config.log.level = 4; break;
```

Аналогично инвертирован `GetLogLevel`. При рестарте службы уровень всегда сбрасывается в неверное значение.

**Временный эффект:** `m_logger->SetLevel(level)` в [`IpcHandler::SetLogLevel`](TcpRedirector/src/service/TcpRedirectorService/adapters/driving/IpcHandler.h:281) устанавливает правильный уровень в памяти, но при рестарте читается неверный из config.json.

### Баг 2: Кнопка Save All не работает

**Анализ:** XAML binding корректен: `Command="{Binding Settings.SaveAsyncCommand}"` в [`MainWindow.xaml`](TcpRedirector/src/gui/TcpRedirectorGUI/MainWindow.xaml:130). Метод `SaveAsync` вызывает `SetRulesAsync` + `SetConfigAsync` + `SetLogLevelAsync`.

**Гипотеза:** `SetConfigAsync` молча падает (исключение или false), но `SetRulesAsync` успевает сохранить правила. Пользователь видит, что правила сохраняются, а proxy-конфиг — нет.

**Необходима доп. диагностика:** Добавить `DiagLog` в `SetConfigAsync` для отслеживания результата IPC-вызова.

### Баг 3: Ротация логов не работает

**Анализ:** Код [`LogRotator`](TcpRedirector/src/service/TcpRedirectorService/infrastructure/logging/LogRotator.cpp) корректен. Ротация происходит:
- По размеру: при превышении 10 MB в [`Logger::WriterThread`](TcpRedirector/src/service/TcpRedirectorService/infrastructure/logging/Logger.cpp:256)
- По расписанию: ежедневно в 03:00 в [`LogRotator::SchedulerThread`](TcpRedirector/src/service/TcpRedirectorService/infrastructure/logging/LogRotator.cpp:74)

**Вероятная причина:** Пользователь не дождался 03:00 или лог-файл не достиг 10 MB. Нужно добавить сообщение в лог при старте ротатора для подтверждения, что он запущен.

### Баг 4: Неиспользуемые поля в config.json

**Анализ:** Все поля используются:
- `app.exePath` → WinDivertCapture
- `auth.*` → аутентификация
- `log.*` → логирование
- `log_rotation.*` → LogRotator
- `proxy.*` → прокси
- `rules` → правила
- `stats.updateIntervalMs` → GUI polling

Пользователь, вероятно, имел в виду `log_rotation` (раз ротация не работает).
